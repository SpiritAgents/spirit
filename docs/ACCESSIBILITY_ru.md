Spirit активно разрабатывается. В этом заявлении описаны текущая работа над доступностью, поддерживаемые рабочие процессы и охват проверки.

## Приоритеты и текущая работа

Текущая работа Spirit над доступностью сосредоточена на управлении с клавиатуры, видимом фокусе, осмысленной семантике элементов управления и уменьшении движения в общем React Workbench, используемом Desktop и необязательным веб-хостом.

В [PR № 437: fix(web): improve keyboard navigation and focus indicators](https://github.com/SpiritAgents/spirit/pull/437) реализовано и протестировано следующее поведение в охваченных представлениях:

- Общие [примитивы перемещающегося фокуса](../packages/ui/src/roving-focus-group.tsx) для линейных списков, визуальных сеток, виртуализированных списков и действий текущей строки.
- Навигация клавишами со стрелками, а также Home и End там, где это реализовано, в списках моделей и поставщиков, вкладках и каталогах источников расширений, списках и истории автоматизаций, деревьях файлов рабочей области, списках Git, вкладках инструментов и боковой панели сеансов.
- Одна основная точка входа по Tab для охваченных составных списков с сохранением доступа к действиям текущей строки с клавиатуры.
- Отображение сведений об элементе при фокусе с клавиатуры в общей реализации всплывающих подсказок, закрытие при потере фокуса или нажатии Escape и связывание описаний через `aria-describedby`.
- Индикаторы фокуса, отличные от оформления наведения указателя, включая строки боковой панели и встроенные действия.

В Workbench также есть настройка уменьшения движения с вариантами «Система», «Включено» и «Выключено». [Реализация](../packages/web/src/lib/reduce-motion.ts) в системном режиме следует параметру операционной системы `prefers-reduced-motion` и предоставляет общее состояние документа для стилей и поведения, учитывающих движение.

В части интерфейса React используются нативные элементы управления, роли ARIA, доступные имена, атрибуты состояния `aria-current`, `aria-expanded` и `aria-selected`, а также роли status и alert. Общий помощник значков по умолчанию скрывает декоративные значки от вспомогательных технологий, если не заданы свойства доступности или дочернее содержимое. Эта реализация предоставляет семантические средства для вспомогательных технологий. Текущая проверка сосредоточена на клавиатуре и фокусе.

## Требования к участникам

Люди и агенты программирования, изменяющие интерактивный интерфейс, должны:

- Сохранять управление с клавиатуры, видимый фокус и осмысленные имена, роли и состояния. По возможности повторно использовать существующие общие элементы управления и примитивы перемещающегося фокуса.
- Разделять перемещение фокуса и активацию, если установленный шаблон элемента управления прямо не связывает их. Для действий, ранее ориентированных на указатель, также сохранять клавиатурный путь.
- Добавлять или обновлять целевые регрессионные тесты для измененного поведения. Существующие примеры: [тесты перемещающегося фокуса](../packages/web/test/components/roving-focus-group.test.tsx), [тесты составных списков](../packages/web/test/components/keyboard-lists.test.tsx), [клавиатурные тесты боковой панели](../packages/web/test/components/session-sidebar-keyboard.test.tsx) и [клавиатурные тесты рабочей области](../packages/web/test/components/workspace-keyboard.test.tsx).
- Запускать соответствующие проверки и сообщать об охвате проверки. Для изменений Workbench доступны следующие команды пакета:

```bash
pnpm --filter @spiritagent/web test
pnpm --filter @spiritagent/web typecheck
```

[Рабочий процесс Verify](../.github/workflows/verify.yml) запускает сборку, тесты, проверку типов, oxlint и oxfmt для TypeScript, а также проверки Rust. Общие указания по репозиторию приведены в [руководстве для участников](../CONTRIBUTING.md#testing-and-ci).

Vitest и jsdom предоставляют доказательства регрессионных проверок, а тестирование со вспомогательными технологиями документируется отдельно. В запросах на слияние следует указывать соответствующие ручные проверки и пробелы в проверке.

## Сообщить о барьерах доступности

[Сообщите о барьере доступности через форму отчета об ошибке Spirit](https://github.com/SpiritAgents/spirit/issues/new?template=bug_report.md). Включите «Accessibility» в заголовок issue, чтобы отчет было легко распознать.

Опишите затронутую задачу или страницу, ожидаемое и фактическое поведение. Полезный контекст может включать версию Spirit, операционную систему, способ ввода, браузер при использовании веб-хоста и применяемые вспомогательные технологии. Делитесь только той информацией, которую готовы раскрыть.

Для отчета достаточно текстового описания. Сведения об инвалидности, снимки экрана, записи и журналы предоставляются по желанию. Добавляйте материалы, если они помогут разобраться в проблеме и вы готовы ими поделиться. Удаляйте ключи API, токены и личные пути из журналов перед публикацией.

## Реагирование и отслеживание

Отчеты о доступности используют тот же рабочий процесс GitHub issue и запросов на слияние, что и другие ошибки Spirit. Сопровождающие оценивают и определяют приоритет отчетов при сортировке. Статус и обсуждение реализации фиксируются в issue и связанных запросах на слияние.

## Охват по средам

- **Desktop:** оболочка Spirit на Electron предназначена для Windows, macOS и Linux.
- **Веб-хост:** Desktop и необязательный веб-хост используют общий рендерер React Workbench и его регрессионный набор тестов клавиатурного фокуса.
- **Ввод с клавиатуры:** автоматические тесты охватывают описанные выше конкретные действия навигации и фокуса в общем React Workbench.
- **Экранные дикторы и другие вспомогательные технологии:** исходный код включает семантические элементы управления, доступные имена, атрибуты состояния и динамические статусные элементы. Подробные результаты для конкретных вспомогательных технологий можно добавлять по мере их проверки.
- **CLI и терминальный интерфейс:** Spirit включает CLI на Rust и необязательный терминальный интерфейс. Оценка доступности этих хостов остается открытой областью работы.

## Текущие пробелы в охвате

- Работа над клавиатурой в PR № 437 охватывает определенные представления React и общие примитивы. Содержимое редактора Monaco, встроенные терминалы, браузер внутри приложения, интерфейс расширений и другое встроенное или стороннее содержимое являются дополнительными областями для оценки.
- Потоковые сообщения, динамические обновления, диалоги и сложное содержимое еще предстоит оценить в сквозных тестах с экранными дикторами. Существующие тесты сосредоточены на ролях DOM и клавиатурных взаимодействиях.

## Ответственность и сопровождение

Сопровождающие Spirit рассматривают изменения этого заявления через обычный процесс запросов на слияние проекта.

Участники, изменяющие поддерживаемое поведение, покрытие тестами или известные барьеры, должны предлагать соответствующие обновления этого заявления в том же запросе на слияние. Переводы должны сохранять различие английской версии между реализованным поведением и состоянием его проверки.
