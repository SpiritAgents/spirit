Eine Erweiterung ist ein Ordner mit einer `.spirit/extension.json` — dem Spirit-Manifest-Dump — neben einem reinen npm-`package.json`. Spirit installiert Erweiterungen pro Benutzer und pro Host, nicht unter dem `.spirit/`-Verzeichnis des Workspaces, und begrenzt jede Installation auf den Marktplatz, aus dem sie stammt: Die Installationsidentität ist `(Quellen-ID, Name)`.

| Host    | Pfad                                                    |
| ------- | ------------------------------------------------------- |
| Desktop | `{spiritDataDir}/extensions/desktop/<sourceId>/<name>/` |
| CLI     | `{spiritDataDir}/extensions/cli/<sourceId>/<name>/`     |

Das unterscheidet sich von [Skills](../customize/skills.mdx) (`SKILL.md`-Ordner), [MCP](../customize/mcp.mdx) (externe Server) und [Hooks](../customize/hooks.mdx) (`hooks.json`-Skripte). `contributes.cli.hooks` gestaltet CLI-TUI-Slots. Es ist nicht `hooks.json`. Eine Erweiterung kann dieselben Dateien dennoch _bündeln_, wenn sie `mcp`, `hooks`, `skills` oder `rules` deklariert.

Jede installierte Erweiterung hat einen Aktivierungsschalter. Deaktiviere oder deinstalliere sie, um ihre Beiträge zu stoppen. Das Einschalten der Erweiterung ist die Zustimmung, die deklarierten MCP-Server, Agent-Hooks, Skills und Rules auszuführen.

Der Assistent fragt nach einem Erweiterungsnamen (kebab-case), einem Anzeigenamen, einer einzeiligen Beschreibung und den zu gerüstenden Fähigkeiten. Er schreibt `package.json`, `icon.svg` und `.spirit/extension.json`, plus die Dateien zu den gewählten Fähigkeiten (`skills/<name>/SKILL.md`, `rule.md`, `mcp.json`, `hooks.json`, `styles.css`, `index.mjs`), und gibt am Ende einen fertigen Marktplatz-Eintrag zum Einfügen aus.

Für Skripte hat jede Frage ein Flag: `[target-dir]`, `--name`, `--display-name`, `--description`, `--capabilities <csv>` und `--yes` zum Überspringen der Bestätigung.

Validiere das Ergebnis jederzeit:

```bash
npx @spiritagent/extension-toolkit check ./my-extension
```

Ein Erweiterungsverzeichnis braucht nur zwei Dateien — `.spirit/extension.json` und `package.json` — plus die Fähigkeitsdateien, die es deklariert:

```text
my-extension/
  .spirit/
    extension.json        # Spirit-Manifest-Dump (erforderlich)
  package.json            # reines npm; nur `main` wird gelesen
  icon.svg                # optional; nur SVG, kein <script>
  index.mjs               # optional; der von `main` referenzierte activate-Einstieg
  mcp.json                # bei Deklaration von mcp
  hooks.json              # bei Deklaration von hooks (Agent-Hooks)
  rule.md                 # bei Deklaration von rules
  skills/<name>/SKILL.md  # bei Deklaration von skills
  styles.css              # bei Deklaration von Desktop-CSS (Pfad im Manifest referenziert)
  cli-hooks.json          # bei Deklaration von CLI-Hooks (Pfad im Manifest referenziert)
```

`package.json` trägt keine Spirit-Felder — `name`, `version`, `description`, `author`, `homepage`, `license`, `main`, `keywords` bleiben reines npm. Der Host liest nur `main`, den Moduleinstieg für [`activate`](#activate).

`.spirit/extension.json`-Felder:

| Feld            | Beschreibung                                                                                                                                                                    |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schemaVersion` | Erforderlich. Muss `1` sein                                                                                                                                                     |
| `name`          | Erforderlich. kebab-case; die Eintrags-ID innerhalb eines Marktplatzes                                                                                                          |
| `version`       | Erforderlich. Semver `major.minor.patch`; Pre-Release-Suffixe werden nicht unterstützt                                                                                          |
| `sourceId`      | Erforderlich. Quellen-ID des besitzenden Marktplatzes. ZIP-Pakete deklarieren selbst einen beliebigen Wert (z. B. `"self-declared"`); die Installationspipeline schreibt ihn um |
| `displayName`   | Erforderlich. Für den Benutzer sichtbarer Name                                                                                                                                  |
| `description`   | Erforderlich. Einzeilige Zusammenfassung                                                                                                                                        |
| `icon`          | Optional. SVG-Pfad relativ zum Erweiterungsstamm                                                                                                                                |
| `author`        | Optional. `{ name, email?, url? }` oder ein String im npm-Stil `"Name <email> (url)"`                                                                                           |
| `category`      | Optional. Einzelner String                                                                                                                                                      |
| `keywords`      | Optional. String-Array mit Suchbegriffen                                                                                                                                        |
| `manifest`      | Erforderlich. Die Laufzeitdeklaration — siehe den Abschnitt „Das `manifest`“                                                                                                    |

Der Dump trägt kein `source` und keine Kuratierungsfelder (`reviewStatus`, `featured`) — die gehören zum Marktplatz-Eintrag.

Deklarierte Dateien müssen existieren und gültig sein: Wer `mcp`, `hooks`, `skills` oder `rules` ohne die passende Datei deklariert, scheitert an Validierung und Installation. Vorhandene, aber nicht deklarierte Dateien werden ignoriert und nie geladen.

## Das `manifest`

Das `manifest`-Objekt ist die Laufzeitdeklaration der Erweiterung: welche Hosts sie unterstützt, wann sie aktiviert wird und was sie beiträgt. In einem Marktplatz-Eintrag wird das Manifest vom Marktplatz-Betreiber bestätigt; in einem ZIP-Paket ist es selbstdeklariert und durch die Prüfungsbestätigung abgesichert.

### Fähigkeiten

| Wert                 | Laufzeit                                                                                 |
| -------------------- | ---------------------------------------------------------------------------------------- |
| `tool-definitions`   | Erforderlich mit `tool-execution`, um `contributes.tools` für das Modell bereitzustellen |
| `tool-execution`     | Erforderlich mit `tool-definitions`, um diese Werkzeuge auszuführen                      |
| `system-prompt`      | Erforderlich mit `main`, um einen Systemprompt-Fragment beizutragen                      |
| `desktop-ui`         | Muss mit `contributes.desktop` gepaart sein                                              |
| `cli-ui`             | Muss mit `contributes.cli` gepaart sein                                                  |
| `mcp`                | Muss mit `contributes.mcp` gepaart sein; lädt `mcp.json` im Paketstamm                   |
| `hooks`              | Muss mit `contributes.hooks` gepaart sein; lädt `hooks.json` im Paketstamm               |
| `skills`             | Muss mit `contributes.skills` gepaart sein; lädt `skills/<name>/SKILL.md`                |
| `rules`              | Muss mit `contributes.rules` gepaart sein; lädt `rule.md` im Paketstamm                  |
| `approval-flow`      | Nur deklariert. Die Genehmigung wird durch den `approvalMode` jedes Tools gesteuert      |
| `questions-flow`     | Nur deklariert. Fragen werden durch `approvalMode: need-questions` gesteuert             |
| `settings`           | Nur deklariert. Einstellungen kommen aus `settingsSchema`                                |
| `secret-storage`     | Wird mit `secretSlots` verwendet                                                         |
| `structured-results` | Nur deklariert                                                                           |

`desktop-ui` / `cli-ui` / `mcp` / `hooks` / `skills` / `rules` und der passende `contributes`-Eintrag müssen entweder beide vorhanden oder beide nicht vorhanden sein.

### Aktivierungsereignisse

| Ereignis               | Wann es ausgelöst wird                      |
| ---------------------- | ------------------------------------------- |
| `onStartup`            | Host-Aufwärmphase                           |
| `onExtensionInstalled` | Nach abgeschlossener Installation           |
| `onSessionOpened`      | Sitzung wird aktiv                          |
| `onSessionReset`       | Sitzung wird zurückgesetzt                  |
| `onUserMessage`        | Benutzer sendet eine Nachricht              |
| `onToolCall`           | Ein Tool wird gleich ausgeführt             |
| `onToolResult`         | Ein Tool-Ergebnis ist verfügbar             |
| `onApprovalResolved`   | Eine Genehmigungsentscheidung ist aufgelöst |

Der Host ruft `activate` auf, wenn die Erweiterung das Ereignis auflistet und eine lesbare `main` hat.

### `contributes.tools`

| Feld            | Beschreibung                                               |
| --------------- | ---------------------------------------------------------- |
| `name`          | Erforderlich. `[a-z0-9]+(?:[._-][a-z0-9]+)*`               |
| `description`   | Erforderlich. Wird dem Modell angezeigt                    |
| `inputSchema`   | Erforderlich. JSON-Schema-Objekt                           |
| `outputSchema`  | Optional. JSON-Schema-Objekt                               |
| `approvalMode`  | Optional. `allowed`, `need-approval` oder `need-questions` |
| `executionMode` | Optional. `foreground` oder `background`                   |

Das Modell sieht `name` nicht unverändert. Der Host erstellt einen Aufrufnamen wie `extension__{id}__{tool}__{hash}`.

### `contributes.desktop`

Erfordert `desktop-ui`.

| Feld           | Beschreibung                                                                           |
| -------------- | -------------------------------------------------------------------------------------- |
| `css[].path`   | Erforderlich. CSS-Datei relativ zum Paketstamm                                         |
| `css[].media`  | Optional. CSS-Medienabfrage                                                            |
| `settingsPage` | Optional. `true`, `{}` oder `{ title }` – fügt einen Desktop-Einstellungseintrag hinzu |

### `contributes.cli`

Erfordert `cli-ui`. `hooks` ist ein Objekt mit `path`, kein Inline-Array:

```json
{
  "hooks": { "path": "cli-hooks.json" }
}
```

Die Datei muss `{ "hooks": [ ... ] }` sein.

| Feld      | Beschreibung                                                             |
| --------- | ------------------------------------------------------------------------ |
| `slot`    | Erforderlich. Einer der folgenden Slots                                  |
| `variant` | Optional. `default`, `accented`, `muted`, `warning`, `success`, `danger` |
| `tokens`  | Optional. `{ foreground?, border?, accent? }`                            |
| `prefix`  | Optional. String                                                         |
| `suffix`  | Optional. String                                                         |

Slots: `message.user`, `message.assistant`, `message.tool`, `assistant.thinking`, `input.frame`, `bottom_form`, `bottom_form.section`, `slash_suggestions`, `approval.panel`, `questions.panel`.

Token-Rollen: `default`, `primary`, `secondary`, `muted`, `accent`, `success`, `warning`, `danger`.

```json
{
  "hooks": [
    {
      "slot": "input.frame",
      "variant": "accented",
      "tokens": { "border": "accent" },
      "prefix": "[",
      "suffix": "]"
    }
  ]
}
```

### Gebündelte MCP, Hooks, Skills und Rules

Erfordert die passende Capability. `contributes.mcp`, `contributes.hooks`, `contributes.skills` und `contributes.rules` sind `true` oder `{}`. Die Pfade sind konventionell; eigene Pfade sind nicht erlaubt.

| Beitrag     | Capability | Datei                                                                                       |
| ----------- | ---------- | ------------------------------------------------------------------------------------------- |
| MCP         | `mcp`      | `mcp.json` im Paketstamm (gleiches Schema wie Benutzer-/Workspace-MCP)                      |
| Agent-Hooks | `hooks`    | `hooks.json` im Paketstamm (gleiches Schema wie Agent-Hooks; nicht `contributes.cli.hooks`) |
| Skills      | `skills`   | `skills/<name>/SKILL.md`                                                                    |
| Rules       | `rules`    | `rule.md` im Paketstamm                                                                     |

Deklariert, aber fehlend oder ungültig: Installation schlägt fehl. Vorhandene, aber nicht deklarierte Dateien werden ignoriert und nie geladen.

Relative `command`- und `cwd`-Werte beziehen sich auf den Erweiterungsstamm. Fehlt `cwd` bei MCP-stdio, ist der Erweiterungsstamm der Standard.

Diese Beiträge werden zur Laufzeit in die Sitzung gelegt, wenn die Erweiterung aktiviert ist. Sie erscheinen nicht unter **Einstellungen → MCPs | Hooks | Skills | Rules**. Bei Namenskonflikten gilt Workspace vor Benutzer vor Erweiterung.

### `settingsSchema`

| Feld           | Beschreibung                                                          |
| -------------- | --------------------------------------------------------------------- |
| `key`          | Erforderlich. Gleiches Muster wie Tool-Namen                          |
| `type`         | Erforderlich. `string`, `boolean`, `number` oder `select`             |
| `title`        | Erforderlich. UI-Label                                                |
| `description`  | Optional                                                              |
| `placeholder`  | Optional                                                              |
| `required`     | Optional. Boolean                                                     |
| `defaultValue` | Optional. Muss mit `type` übereinstimmen                              |
| `options`      | Erforderlich für `select`. Array von `{ value, label, description? }` |

Werte sind `string`, `number`, `boolean` oder `null`. `null` löscht eine nicht erforderliche Einstellung.

### `secretSlots`

| Feld          | Beschreibung      |
| ------------- | ----------------- |
| `key`         | Erforderlich      |
| `title`       | Erforderlich      |
| `description` | Optional          |
| `required`    | Optional. Boolean |

Desktop speichert Geheimnisse im OS-Keyring. Beim CLI-Daemon-Pfad sind `secrets.set` / `secrets.delete` möglicherweise nicht verfügbar.

## `activate`

`main` wird mit dynamischem `import` geladen. Exportieren Sie eines von:

- `export function activate(ctx) { ... }`
- `export default function activate(ctx) { ... }`
- `export default { activate }`

### `ctx`

| Feld              | Beschreibung                                                                                                 |
| ----------------- | ------------------------------------------------------------------------------------------------------------ |
| `extension`       | `{ id, name, version, directoryPath, manifestPath, main }`                                                   |
| `host`            | Host-API. Desktop implementiert `showMessageBox`. CLI ist `{}`                                               |
| `log`             | `(message: string) => void`                                                                                  |
| `settings`        | `get(key)`, `getAll()`, `set(key, value)`, `setAll(values)`                                                  |
| `secrets`         | `get(key)`, `has(key)`, `set(key, value)`, `delete(key)` — Schlüssel müssen in `secretSlots` deklariert sein |
| `activationEvent` | Optional. `{ type, detail? }`                                                                                |

### Rückgabewert

Geben Sie ein Objekt zurück oder exportieren Sie dieselben Felder aus dem Modul.

| Feld              | Beschreibung                                                                                  |
| ----------------- | --------------------------------------------------------------------------------------------- |
| `tools`           | `Record<string, (ctx) => unknown>`. Schlüssel sind Manifest-Toolnamen                         |
| `invokeTool`      | `(ctx) => unknown`. Wird anstelle von `tools[name]` verwendet, wenn vorhanden                 |
| `systemPrompt`    | Statisches Systemfragment                                                                     |
| `getSystemPrompt` | `() => string \| Promise<string>`. Wird anstelle von `systemPrompt` verwendet, wenn vorhanden |
| `onEvent`         | `(event) => void`                                                                             |
| `dispose`         | `() => void`. Wird beim Entfernen oder Neuladen aufgerufen                                    |

### Tool-Handler `ctx`

| Feld              | Beschreibung                                                   |
| ----------------- | -------------------------------------------------------------- |
| `extension`       | Gleiche Laufzeitinformationen wie `activate`                   |
| `host`            | Gleiche Host-API                                               |
| `toolName`        | Manifest-Toolname                                              |
| `arguments`       | Objekt vom Modell                                              |
| `log`             | Gleicher Logger                                                |
| `settings`        | Gleicher Settings-Zugriff                                      |
| `secrets`         | Gleicher Secrets-Zugriff                                       |
| `toolCallId`      | Optional                                                       |
| `questionsResult` | Optional. Festgelegt, wenn `approvalMode` `need-questions` ist |

Ein `string`-Ergebnis wird durchgereicht. Andere Werte werden `JSON.stringify(value, null, 2)`. `undefined` wird zu `""`.

### Desktop `host.showMessageBox`

| Feld        | Beschreibung                                             |
| ----------- | -------------------------------------------------------- |
| `title`     | Erforderlich. Zeichenkette                               |
| `message`   | Erforderlich. Zeichenkette                               |
| `detail`    | Optional. Zeichenkette                                   |
| `buttons`   | Optional. Zeichenkettenarray                             |
| `cancelId`  | Optional. Zahl                                           |
| `defaultId` | Optional. Zahl                                           |
| `noLink`    | Optional. Boolesch                                       |
| `type`      | Optional. `none`, `info`, `error`, `question`, `warning` |

```js
export function activate(ctx) {
  return {
    systemPrompt: "Use lookup_item when the user asks for an item by id.",
    async invokeTool({ toolName, arguments: args, settings, secrets }) {
      if (toolName !== "lookup_item") {
        throw new Error(`Unknown tool: ${toolName}`);
      }
      const region = await settings.get("region");
      const token = await secrets.get("api_token");
      return { id: args.id, region, hasToken: Boolean(token) };
    },
    dispose() {
      ctx.log("example-extension disposed");
    },
  };
}
```

## Als ZIP verteilen

Packe ein Erweiterungsverzeichnis in das teilbare ZIP-Format (Inhalt plus `.spirit/extension.json`):

```bash
npx @spiritagent/extension-toolkit pack ./my-extension
```

Der Befehl validiert das Paket zuerst und schreibt `<name>-<version>.zip` in das aktuelle Verzeichnis. Benutzer importieren das ZIP über die Seite **Erweiterungen** oder mit `spirit extension import`; es landet in ihrem persönlichen Marktplatz. Siehe [Erweiterungen](../customize/extensions.mdx).

## Einen entfernten Erweiterungsmarktplatz betreiben

Ein entfernter Erweiterungsmarktplatz ist ein bereitstellbares Verzeichnis mit einem `.spirit/marketplace.json`-Index: ein Git-Repository, eine statische Site oder ein lokales Verzeichnis. Benutzer fügen ihn mit `spirit extension marketplace add <url|path>` oder über die Desktop-Seite **Erweiterungen** hinzu und stöbern dann in seinen Einträgen und installieren sie.

<Tabs items={["Template-Repository", "Manuell"]}>
<Tab value="Template-Repository">

[Use this template](https://github.com/new?template_owner=SpiritAgents&template_name=extension-template) erstellt dein eigenes Marktplatz-Repository aus `SpiritAgents/extension-template`.

Das Template bringt das Registry-Layout, zwei Beispiel-Erweiterungen und CI mit, die die Registry bei jedem Push und Pull Request validiert. So veröffentlichst du eine Erweiterung:

1. Gerüste sie mit `npm create @spiritagent/extension`.
2. Verschiebe den Erweiterungsordner nach `extensions/`.
3. Füge den Registry-Eintrag, den der Assistent ausgegeben hat, in `.spirit/marketplace.json` ein.
4. Pushe — Benutzer fügen den Marktplatz über seine Git-URL hinzu.

</Tab>
<Tab value="Manuell">

Ein Marktplatz-Stamm enthält den Index plus ein Inhaltsverzeichnis pro Erweiterung:

```text
my-marketplace/
  .spirit/
    marketplace.json  # der Index
  extensions/
    my-extension/     # Inhaltsverzeichnis (reines npm-Paket + Fähigkeitsdateien)
      icon.svg
      package.json
      ...
```

Relative Pfade in `marketplace.json` lösen gegen den Marktplatz-Stamm auf und dürfen weder `..`-Segmente noch absolute Pfade enthalten.

Eintragsfelder nach Gruppen:

- **Identität** — `name` (kebab-case; die Eintrags-ID), `version` (Semver, kein Pre-Release) und `source`: ein stammrelativer Pfad-String wie `"./extensions/my-extension"` für lokalen Inhalt oder `{ "source": "npm", "package": "@scope/name@1.0.0" }`, um eine exakte npm-Version festzupinnen (die Integrität wird bei der Installation gegen den SRI-Hash des Packuments geprüft).
- **Anzeige** — `displayName`, `description`, `icon` (stammrelativer SVG-Pfad), `category`, `keywords`, `author`.
- **Deklaration** — `manifest`: die im Abschnitt „Das `manifest`“ beschriebene Laufzeitdeklaration. Der Marktplatz bestätigt sie; ein Paket kann Fähigkeiten nicht von sich aus behaupten.
- **Kuratierung** — `featured` und `reviewStatus` (`unverified` / `verified` / `revoked`).

Validiere die Registry lokal — offline: Schema, kebab-case-Namen, Semver ohne Pre-Release, npm-Source-Format, deklarierte Beitragsdateien für lokale Sources und Icon-Regeln:

```bash
npx -y @spiritagent/extension-toolkit marketplace check .
```

Prüfungsdisziplin: Pull Requests, die einen Eintrag hinzufügen oder seine `version` ändern, müssen `reviewStatus: "unverified"` beibehalten; die Beförderung zu `verified` erfolgt in einem separaten Commit nach menschlicher Prüfung. Die `.github/workflows/marketplace.yml` des Template-Repositorys ist eine Referenzimplementierung — sie difft den Index gegen die PR-Basis.

</Tab>
</Tabs>

### Lokale Marktplätze

Jedes lokale Verzeichnis mit einer `.spirit/marketplace.json` funktioniert als Marktplatz — füge es mit `spirit extension marketplace add <path>` oder auf dem Desktop über **Von Festplatte hinzufügen…** hinzu. Lokale Marktplätze werden an Ort und Stelle gelesen und brauchen keine CI, was sie zum Entwicklungsloop für Erweiterungsautoren macht: bearbeiten, neu installieren, wiederholen.
