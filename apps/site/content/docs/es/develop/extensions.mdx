Una extensión es una carpeta con un `.spirit/extension.json` — el volcado de manifiesto de Spirit — junto a un `package.json` puramente npm. Spirit instala extensiones por usuario y por host, no bajo el directorio `.spirit/` del espacio de trabajo, y delimita cada instalación por el mercado del que proviene: la identidad de instalación es `(id de fuente, name)`.

| Host    | Ruta                                                    |
| ------- | ------------------------------------------------------- |
| Desktop | `{spiritDataDir}/extensions/desktop/<sourceId>/<name>/` |
| CLI     | `{spiritDataDir}/extensions/cli/<sourceId>/<name>/`     |

Esto es diferente de [Skills](../customize/skills.mdx) (carpetas `SKILL.md`), [MCP](../customize/mcp.mdx) (servidores externos) y [Hooks](../customize/hooks.mdx) (scripts `hooks.json`). `contributes.cli.hooks` da estilo a los slots de la TUI de la CLI. No es `hooks.json`. Una extensión aún puede _empaquetar_ esos mismos archivos cuando declara `mcp`, `hooks`, `skills` o `rules`.

Cada extensión instalada tiene un interruptor de activación. Desactívala o desinstálala para detener sus contribuciones. Activar la extensión es consentir la ejecución de los servidores MCP, hooks de agente, skills y rules que declaró.

El asistente pregunta un nombre de extensión (kebab-case), un nombre visible, una descripción de una línea y las capacidades a generar. Escribe `package.json`, `icon.svg` y `.spirit/extension.json`, más los archivos de las capacidades elegidas (`skills/<name>/SKILL.md`, `rule.md`, `mcp.json`, `hooks.json`, `styles.css`, `index.mjs`), y al terminar imprime una entrada de mercado lista para pegar.

Para scripting, cada pregunta tiene un flag: `[target-dir]`, `--name`, `--display-name`, `--description`, `--capabilities <csv>` y `--yes` para omitir la confirmación.

Valida el resultado en cualquier momento:

```bash
npx @spiritagent/extension-toolkit check ./my-extension
```

</Tab>
<Tab value="Manual">

Un directorio de extensión solo necesita dos archivos — `.spirit/extension.json` y `package.json` — más los archivos de las capacidades que declare:

```text
my-extension/
  .spirit/
    extension.json        # volcado de manifiesto de Spirit (obligatorio)
  package.json            # puramente npm; solo se lee `main`
  icon.svg                # opcional; solo SVG, sin <script>
  index.mjs               # opcional; la entrada de activate referenciada por `main`
  mcp.json                # al declarar mcp
  hooks.json              # al declarar hooks (hooks de agente)
  rule.md                 # al declarar rules
  skills/<name>/SKILL.md  # al declarar skills
  styles.css              # al declarar CSS de desktop (ruta referenciada desde el manifiesto)
  cli-hooks.json          # al declarar hooks de CLI (ruta referenciada desde el manifiesto)
```

`package.json` no lleva ningún campo de Spirit — `name`, `version`, `description`, `author`, `homepage`, `license`, `main`, `keywords` siguen siendo puramente npm. El host solo lee `main`, la entrada de módulo de [`activate`](#activate).

Campos de `.spirit/extension.json`:

| Campo           | Descripción                                                                                                                                                                  |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schemaVersion` | Obligatorio. Debe ser `1`                                                                                                                                                    |
| `name`          | Obligatorio. kebab-case; el id de la entrada dentro de un mercado                                                                                                            |
| `version`       | Obligatorio. Semver `major.minor.patch`; los sufijos de pre-lanzamiento no están soportados                                                                                  |
| `sourceId`      | Obligatorio. Id de la fuente del mercado propietario. Los paquetes ZIP autodeclaran cualquier valor (por ejemplo `"self-declared"`); el pipeline de instalación lo reescribe |
| `displayName`   | Obligatorio. Nombre visible para el usuario                                                                                                                                  |
| `description`   | Obligatorio. Resumen de una línea                                                                                                                                            |
| `icon`          | Opcional. Ruta SVG relativa a la raíz de la extensión                                                                                                                        |
| `author`        | Opcional. `{ name, url? }`                                                                                                                                                   |
| `categories`    | Opcional. Array de cadenas                                                                                                                                                   |
| `manifest`      | Obligatorio. La declaración en tiempo de ejecución — véase la sección «El `manifest`»                                                                                        |

El volcado no lleva `source` ni campos de curaduría (`reviewStatus`, `featured`) — esos pertenecen a la entrada del mercado.

Los archivos declarados deben existir y ser válidos: declarar `mcp`, `hooks`, `skills` o `rules` sin el archivo correspondiente hace fallar la validación y la instalación. Los archivos presentes pero no declarados se ignoran y nunca se cargan.

</Tab>
</Tabs>

## El `manifest`

El objeto `manifest` es la declaración en tiempo de ejecución de la extensión: qué hosts soporta, cuándo se activa y qué contribuye. En una entrada de mercado, el manifiesto está avalado por el operador del mercado; en un paquete ZIP, es autodeclarado y está controlado por la confirmación de revisión.

### Capacidades

| Valor                | Tiempo de ejecución                                                                      |
| -------------------- | ---------------------------------------------------------------------------------------- |
| `tool-definitions`   | Requerido con `tool-execution` para exponer `contributes.tools` al modelo                |
| `tool-execution`     | Requerido con `tool-definitions` para ejecutar esas herramientas                         |
| `system-prompt`      | Requerido con `main` para contribuir con un fragmento de prompt del sistema              |
| `desktop-ui`         | Debe estar emparejado con `contributes.desktop`                                          |
| `cli-ui`             | Debe estar emparejado con `contributes.cli`                                              |
| `mcp`                | Debe estar emparejado con `contributes.mcp`; carga `mcp.json` en la raíz del paquete     |
| `hooks`              | Debe estar emparejado con `contributes.hooks`; carga `hooks.json` en la raíz del paquete |
| `skills`             | Debe estar emparejado con `contributes.skills`; carga `skills/<name>/SKILL.md`           |
| `rules`              | Debe estar emparejado con `contributes.rules`; carga `rule.md` en la raíz del paquete    |
| `approval-flow`      | Solo declarado. La aprobación se rige por el `approvalMode` de cada herramienta          |
| `questions-flow`     | Solo declarado. Las preguntas se rigen por `approvalMode: need-questions`                |
| `settings`           | Solo declarado. La configuración proviene de `settingsSchema`                            |
| `secret-storage`     | Se usa con `secretSlots`                                                                 |
| `structured-results` | Solo declarado                                                                           |

`desktop-ui` / `cli-ui` / `mcp` / `hooks` / `skills` / `rules` y la entrada `contributes` correspondiente deben estar ambos presentes o ambos ausentes.

### Eventos de activación

| Evento                 | Cuándo se dispara                           |
| ---------------------- | ------------------------------------------- |
| `onStartup`            | Calentamiento del host                      |
| `onExtensionInstalled` | Cuando una instalación termina              |
| `onSessionOpened`      | La sesión se vuelve activa                  |
| `onSessionReset`       | Reinicio de sesión                          |
| `onUserMessage`        | El usuario envía un mensaje                 |
| `onToolCall`           | Una herramienta está a punto de ejecutarse  |
| `onToolResult`         | Un resultado de herramienta está disponible |
| `onApprovalResolved`   | Una decisión de aprobación se resuelve      |

El host llama a `activate` cuando la extensión lista el evento y tiene un `main` legible.

### `contributes.tools`

| Campo           | Descripción                                             |
| --------------- | ------------------------------------------------------- |
| `name`          | Requerido. `[a-z0-9]+(?:[._-][a-z0-9]+)*`               |
| `description`   | Requerido. Se muestra al modelo                         |
| `inputSchema`   | Requerido. Objeto JSON Schema                           |
| `outputSchema`  | Opcional. Objeto JSON Schema                            |
| `approvalMode`  | Opcional. `allowed`, `need-approval` o `need-questions` |
| `executionMode` | Opcional. `foreground` o `background`                   |

El modelo no ve `name` tal cual. El host construye un nombre de invocación como `extension__{id}__{tool}__{hash}`.

### `contributes.desktop`

Requiere `desktop-ui`.

| Campo          | Descripción                                                                           |
| -------------- | ------------------------------------------------------------------------------------- |
| `css[].path`   | Requerido. Archivo CSS relativo a la raíz del paquete                                 |
| `css[].media`  | Opcional. Media query CSS                                                             |
| `settingsPage` | Opcional. `true`, `{}` o `{ title }` — agrega una entrada de configuración de Desktop |

### `contributes.cli`

Requiere `cli-ui`. `hooks` es un objeto con `path`, no un array en línea:

```json
{
  "hooks": { "path": "cli-hooks.json" }
}
```

El archivo debe ser `{ "hooks": [ ... ] }`.

| Campo     | Descripción                                                              |
| --------- | ------------------------------------------------------------------------ |
| `slot`    | Requerido. Uno de los slots a continuación                               |
| `variant` | Opcional. `default`, `accented`, `muted`, `warning`, `success`, `danger` |
| `tokens`  | Opcional. `{ foreground?, border?, accent? }`                            |
| `prefix`  | Opcional. Cadena                                                         |
| `suffix`  | Opcional. Cadena                                                         |

Slots: `message.user`, `message.assistant`, `message.tool`, `assistant.thinking`, `input.frame`, `bottom_form`, `bottom_form.section`, `slash_suggestions`, `approval.panel`, `questions.panel`.

Roles de token: `default`, `primary`, `secondary`, `muted`, `accent`, `success`, `warning`, `danger`.

```json
{
  "hooks": [
    {
      "slot": "input.frame",
      "variant": "accented",
      "tokens": { "border": "accent" },
      "prefix": "[",
      "suffix": "]"
    }
  ]
}
```

### MCP, hooks, skills y rules empaquetados

Requieren la capability correspondiente. `contributes.mcp`, `contributes.hooks`, `contributes.skills` y `contributes.rules` son `true` o `{}`. Las rutas son convencionales; no se permiten rutas personalizadas.

| Contribución | Capability | Archivo                                                                                                 |
| ------------ | ---------- | ------------------------------------------------------------------------------------------------------- |
| MCP          | `mcp`      | `mcp.json` en la raíz del paquete (mismo schema que el MCP de usuario/espacio de trabajo)               |
| Agent hooks  | `hooks`    | `hooks.json` en la raíz del paquete (mismo schema que los hooks del agente; no `contributes.cli.hooks`) |
| Skills       | `skills`   | `skills/<name>/SKILL.md`                                                                                |
| Rules        | `rules`    | `rule.md` en la raíz del paquete                                                                        |

Si están declarados pero el archivo falta o es inválido, la instalación falla. Los archivos no declarados se ignoran y nunca se cargan.

`command` y `cwd` relativos se resuelven respecto a la raíz de la extensión. Si un MCP stdio omite `cwd`, el valor predeterminado es la raíz de la extensión.

Estas contribuciones se superponen en la sesión cuando la extensión está habilitada. No aparecen en **Ajustes → MCPs | Hooks | Skills | Rules**. En un conflicto de nombres: espacio de trabajo > usuario > extensión.

### `settingsSchema`

| Campo          | Descripción                                                          |
| -------------- | -------------------------------------------------------------------- |
| `key`          | Requerido. Mismo patrón que los nombres de herramientas              |
| `type`         | Requerido. `string`, `boolean`, `number`, o `select`                 |
| `title`        | Requerido. Etiqueta de interfaz                                      |
| `description`  | Opcional                                                             |
| `placeholder`  | Opcional                                                             |
| `required`     | Opcional. Booleano                                                   |
| `defaultValue` | Opcional. Debe coincidir con `type`                                  |
| `options`      | Requerido para `select`. Arreglo de `{ value, label, description? }` |

Los valores son `string`, `number`, `boolean`, o `null`. `null` limpia un ajuste no requerido.

### `secretSlots`

| Campo         | Descripción        |
| ------------- | ------------------ |
| `key`         | Requerido          |
| `title`       | Requerido          |
| `description` | Opcional           |
| `required`    | Opcional. Booleano |

Desktop almacena secretos en el llavero del sistema. En la ruta del daemon de CLI, `secrets.set` / `secrets.delete` pueden no estar disponibles.

## `activate`

`main` se carga con `import` dinámico. Exporta uno de:

- `export function activate(ctx) { ... }`
- `export default function activate(ctx) { ... }`
- `export default { activate }`

### `ctx`

| Campo             | Descripción                                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------------------- |
| `extension`       | `{ id, name, version, directoryPath, manifestPath, main }`                                              |
| `host`            | API del host. Desktop implementa `showMessageBox`. CLI es `{}`                                          |
| `log`             | `(message: string) => void`                                                                             |
| `settings`        | `get(key)`, `getAll()`, `set(key, value)`, `setAll(values)`                                             |
| `secrets`         | `get(key)`, `has(key)`, `set(key, value)`, `delete(key)` — las claves deben declararse en `secretSlots` |
| `activationEvent` | Opcional. `{ type, detail? }`                                                                           |

### Valor de retorno

Retorna un objeto, o exporta los mismos campos desde el módulo.

| Campo             | Descripción                                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------- |
| `tools`           | `Record<string, (ctx) => unknown>`. Las claves son los nombres de las herramientas del manifiesto |
| `invokeTool`      | `(ctx) => unknown`. Se usa en lugar de `tools[name]` cuando está presente                         |
| `systemPrompt`    | Fragmento estático del sistema                                                                    |
| `getSystemPrompt` | `() => string \| Promise<string>`. Se usa en lugar de `systemPrompt` cuando está presente         |
| `onEvent`         | `(event) => void`                                                                                 |
| `dispose`         | `() => void`. Se llama al eliminar o recargar                                                     |

### `ctx` del manejador de herramientas

| Campo             | Descripción                                                      |
| ----------------- | ---------------------------------------------------------------- |
| `extension`       | La misma información de ejecución que `activate`                 |
| `host`            | La misma API de host                                             |
| `toolName`        | Nombre de la herramienta del manifiesto                          |
| `arguments`       | Objeto del modelo                                                |
| `log`             | El mismo registrador                                             |
| `settings`        | El mismo acceso a configuración                                  |
| `secrets`         | El mismo acceso a secretos                                       |
| `toolCallId`      | Opcional                                                         |
| `questionsResult` | Opcional. Se establece cuando `approvalMode` es `need-questions` |

Un resultado `string` se pasa directamente. Otros valores se convierten con `JSON.stringify(value, null, 2)`. `undefined` se convierte en `""`.

### Escritorio `host.showMessageBox`

| Campo       | Descripción                                              |
| ----------- | -------------------------------------------------------- |
| `title`     | Requerido. Cadena                                        |
| `message`   | Requerido. Cadena                                        |
| `detail`    | Opcional. Cadena                                         |
| `buttons`   | Opcional. Arreglo de cadenas                             |
| `cancelId`  | Opcional. Número                                         |
| `defaultId` | Opcional. Número                                         |
| `noLink`    | Opcional. Booleano                                       |
| `type`      | Opcional. `none`, `info`, `error`, `question`, `warning` |

```js
export function activate(ctx) {
  return {
    systemPrompt: "Use lookup_item when the user asks for an item by id.",
    async invokeTool({ toolName, arguments: args, settings, secrets }) {
      if (toolName !== "lookup_item") {
        throw new Error(`Unknown tool: ${toolName}`);
      }
      const region = await settings.get("region");
      const token = await secrets.get("api_token");
      return { id: args.id, region, hasToken: Boolean(token) };
    },
    dispose() {
      ctx.log("example-extension disposed");
    },
  };
}
```

## Distribuir como ZIP

Empaqueta un directorio de extensión en el formato ZIP compartible (contenido más `.spirit/extension.json`):

```bash
npx @spiritagent/extension-toolkit pack ./my-extension
```

El comando valida primero el paquete y escribe `<name>-<version>.zip` en el directorio actual. Los usuarios importan el ZIP desde la página **Extensiones** o con `spirit extension import`; llega a su mercado Personal. Consulta [Extensiones](../customize/extensions.mdx).

## Operar un mercado de extensiones remoto

Un mercado de extensiones remoto es un directorio servible con un índice `.spirit/marketplace.json`: un repositorio Git, un sitio estático o un directorio local. Los usuarios lo añaden con `spirit extension marketplace add <url|path>` o desde la página **Extensiones** de Desktop, y luego exploran e instalan sus entradas.

<Tabs items={["Repositorio de plantilla", "Manual"]}>
<Tab value="Repositorio de plantilla">

[Use this template](https://github.com/new?template_owner=SpiritAgents&template_name=extension-template) crea tu propio repositorio de mercado a partir de `SpiritAgents/extension-template`.

La plantilla incluye la estructura de registro, dos extensiones de ejemplo y CI que valida el registro en cada push y pull request. Para publicar una extensión:

1. Genérala con `npm create @spiritagent/extension`.
2. Mueve la carpeta de la extensión a `extensions/`.
3. Añade la entrada de registro que imprimió el asistente a `.spirit/marketplace.json`.
4. Haz push — los usuarios añaden el mercado con su URL de Git.

</Tab>
<Tab value="Manual">

Una raíz de mercado contiene el índice más un directorio de contenido por extensión:

```text
my-marketplace/
  .spirit/
    marketplace.json  # el índice
  extensions/
    my-extension/     # directorio de contenido (paquete npm simple + archivos de capacidades)
      icon.svg
      package.json
      ...
```

Las rutas relativas dentro de `marketplace.json` se resuelven contra la raíz del mercado y no deben contener segmentos `..` ni rutas absolutas.

Campos de entrada, por grupo:

- **Identidad** — `name` (kebab-case; el id de la entrada), `version` (semver, sin pre-lanzamiento) y `source`: una cadena de ruta relativa a la raíz como `"./extensions/my-extension"` para contenido local, o `{ "source": "npm", "package": "@scope/name@1.0.0" }` para fijar una versión npm exacta (la integridad se verifica contra el hash SRI del packument en la instalación).
- **Presentación** — `displayName`, `description`, `icon` (ruta SVG relativa a la raíz), `categories`, `author`.
- **Declaración** — `manifest`: la declaración en tiempo de ejecución descrita en la sección «El `manifest`». El mercado la avala; un paquete no puede afirmar capacidades por sí mismo.
- **Curaduría** — `featured` y `reviewStatus` (`unverified` / `verified` / `revoked`).

Valida el registro localmente — sin conexión: esquema, nombres kebab-case, semver sin pre-lanzamiento, formato de fuentes npm, archivos de contribución declarados para fuentes locales y reglas de iconos:

```bash
npx -y @spiritagent/extension-toolkit marketplace check .
```

Disciplina de revisión: los pull requests que añaden una entrada o cambian su `version` deben mantener `reviewStatus: "unverified"`; la promoción a `verified` se hace en un commit separado tras una revisión humana. El `.github/workflows/marketplace.yml` del repositorio de plantilla es una implementación de referencia: compara el índice contra la base del PR.

</Tab>
</Tabs>

### Mercados locales

Cualquier directorio local con un `.spirit/marketplace.json` funciona como mercado — añádelo con `spirit extension marketplace add <path>` o con **Añadir desde disco…** en Desktop. Los mercados locales se leen in situ y no necesitan CI, lo que los convierte en el bucle de desarrollo de los autores de extensiones: editar, reinstalar, repetir.
