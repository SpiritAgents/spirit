Каталог общих пользовательских данных определяется quality сборки, а не каталогом приложений операционной системы.

## Каталог данных

Переопределяется с помощью `SPIRIT_DATA_DIR`. Сервер также может использовать `SPIRIT_SERVER_DATA_DIR` (имеет приоритет над первым).

| Сборка | macOS / Linux                             | Windows                                               |
| ------ | ----------------------------------------- | ----------------------------------------------------- |
| Stable | `~/{{product.stable.userDataFolderName}}` | `%USERPROFILE%\{{product.stable.userDataFolderName}}` |
| Dev    | `~/{{product.dev.userDataFolderName}}`    | `%USERPROFILE%\{{product.dev.userDataFolderName}}`    |

Breaking Change: старые каталоги платформы не читаются и не переносятся автоматически. Явное указание каталога данных по-прежнему поддерживается. Кеш Electron, хранилище браузера и состояние окон остаются в частном каталоге приложения платформы.

Типичные файлы:

```
{spiritDataDir}/
  config.json
  mcp.json
  hooks.json
  rule.md
  skills/
  chats/
  plans/
  extensions/
  automations/
  dreams/
  server.token
  server/instances/
```

Бинарные файлы CLI используют SPIRIT_HOME. В Unix установка Stable и общие данные могут иметь один родительский каталог; bin/ и cli/ остаются файлами установки. Эта настройка не определяет каталог общих данных.

## config.json v1

`schemaVersion` должен быть `1`. Любое другое значение отклоняется — удалите старый файл и [подключите провайдера заново](./providers.mdx). Миграции со старых форм нет.

Основные поля:

- `providers` — подключённые провайдеры: конечная точка, транспорт, учётные данные, модели
- `activeModel`
- `imageGenerationModel` / `videoGenerationModel` / `secondaryLanguageModel`
- `agents` — переключатели агента, например `agents.providerTools.enabled`
- `permission` — правила белого списка разрешений

`activeModel` и другие слоты моделей — это ссылки на модель: `{ "providerId": "…", "name": "…" }`, где `providerId` — это `providers[].id`, а `name` — одно из его `models[].name`.

### Записи провайдеров

Каждая запись `providers[]` — полностью декларативное подключение: что мастер подключения записал, то рантайм и читает. Рантайм никогда не вычисляет `apiBase` заново из идентичности провайдера; выбор сайта, плана и облака материализуется в итоговый URL при подключении.

Поля уровня подключения:

- `id` (обязательно) — уникальный идентификатор записи. На него указывают ссылки на модели и учётная запись внутренней связки ключей
- `label` — необязательное отображаемое имя
- `apiBase` (обязательно) — конечная точка, единственный источник истины
- `transportKind` — wire-протокол: `openai-compatible` (по умолчанию) / `open-responses` / `anthropic` / `bedrock`
- `sdk` — полное имя npm-пакета встроенного SDK-адаптера (например, `@ai-sdk/openai-compatible`). Отсутствует = значение по умолчанию для транспорта; неизвестное имя пакета отклоняется при загрузке
- `headers` — литеральные дополнительные заголовки запроса, добавляемые в каждый исходящий запрос
- `body` — литеральные поля, добавляемые в верхний уровень каждого тела запроса. Запасной выход для wire-особенностей — предпочитайте структурную декларацию, где она есть
- `providerTools` — инструменты, которые предоставляет провайдер (веб-поиск, интерпретатор кода). См. [Инструменты провайдера](./agent/tools.mdx#provider-tools)
- `fileUpload` — канал загрузки для локальных файлов, которые не должны идти инлайн (`path` / `url`, `purpose`, `idPath`, `refTemplate`, `maxBytes`). Отсутствует = медиа идут инлайн
- `imageApi` / `videoApi` — имена формы API для генерации изображений / видео; отсутствует = такой генерации нет
- `options` — параметры транспорта; допустимый набор ключей зависит от `transportKind` × `sdk` (`awsRegion` для bedrock, `project` / `location` для `@ai-sdk/google-vertex`, переключатели `auth` / `storedState` / `applyPatch` для open-responses). Неизвестные ключи отклоняются
- `models` (обязательный массив, может быть пустым)

Поля уровня модели — `capabilities`, `contextLength`, `outputLimit`, `reasoningEffort`, `supportedReasoningEfforts`, `reasoningMode`, `supportedReasoningModes`, `supportsThinkingType`, `supportsThinkingSwitch`, `thinkingSwitch`, `serviceTiers`, `serviceTier` — также можно объявить плоско на записи провайдера как значения по умолчанию, наследуемые всеми её моделями; собственная декларация модели побеждает. Внутри `models[]` всё, кроме `name`, необязательно, и отсутствие означает «не объявлено», а не значение по умолчанию.

- Токены `capabilities`: `languageModel`, `image`, `audio`, `video`, `imageGeneration`, `videoGeneration`
- `outputLimit` — предел выходных токенов, отдельно от `contextLength`
- `supportedReasoningEfforts` / `supportedReasoningModes` / `serviceTiers` — единственный источник для выбора и валидации: выбор значения вне списка — ошибка при загрузке, а не молчаливое ограничение
- `thinkingEnabled` — ваше состояние thinking вкл/выкл (не декларация возможности); только на уровне модели и требует объявленного `supportsThinkingSwitch`

### Каналы ключей

Ключи не обязаны храниться в этом файле — мастер подключения по умолчанию записывает их прямо в [связку ключей](./security.mdx). Конфиг вместо этого может объявить канал, разрешаемый в таком порядке:

1. `apiKey` — открытый текст. Не рекомендуется; только запасной выход
2. `apiKeyEnv` — имя переменной окружения, из которой читать ключ
3. `apiKeyKeyring` — `{ "service": "…", "account": "…" }`, запись во внешней связке ключей
4. Внутренняя связка ключей — неявный запасной вариант, который записывает мастер (учётная запись `provider::{id}`)

Составные учётные данные (Bedrock IAM, сервисные аккаунты Vertex) вместо плоских ключей используют карту слотов `credentials`:

```json
{
  "credentials": {
    "accessKeyId": { "env": "AWS_ACCESS_KEY_ID" },
    "secretAccessKey": { "keyring": { "service": "…", "account": "…" } }
  }
}
```

Имена слотов — поля протокола: `apiKey`, `accessKeyId` / `secretAccessKey` (Bedrock IAM / SigV4), `clientEmail` / `privateKey` (Vertex); неизвестные слоты отклоняются. Каждый слот разрешается как `value` → `env` → `keyring` → внутренняя связка ключей (`provider::{id}::{slot}`; слот `apiKey` — это просто `provider::{id}`). Плоские ключи и `credentials.apiKey` не могут сосуществовать в одной записи.

### agents.providerTools

`agents.providerTools.enabled` управляет сразу всеми инструментами, объявленными провайдерами (переименовано из `agents.webSearch.enabled`; семантика не изменилась: opt-out, включено по умолчанию). При значении `false` ни записи инструментов провайдера, ни переключатели body не попадают в запросы.

### Обновление каталога и переподключение

Регулярные обновления каталога перезаписывают поля декларации модели, которыми владеет каталог (`capabilities`, `supportedReasoningEfforts`, `supportedReasoningModes`, `serviceTiers` и т. д.) — факты о моделях берутся из каталога как единственного источника истины, поэтому ручные правки этих полей перезаписываются при следующем обновлении. Материализации уровня провайдера (`apiBase`, `sdk`, `providerTools`, `fileUpload`, `options`, `imageApi` / `videoApi`) меняются только при переподключении провайдера. Переподключение сбрасывает ключи, принадлежащие мастеру (ваши правки в них перезаписываются), и сохраняет всё остальное: `label`, каналы учётных данных, `headers` / `body`, плоские значения по умолчанию моделей и добавленные вами вручную модели.

### permission

`permission` точно задаёт, что разрешено отдельным shell-командам и путям к файлам, поверх [уровня подтверждения](./agent/approvals.mdx) сессии. Ключи — имена инструментов (`shell`, `read_file`); значения сопоставляют подстановочные шаблоны действиям `allow`, `ask` или `deny`.

```json
{
  "permission": {
    "shell": {
      "git *": "allow",
      "rm -rf *": "deny"
    }
  }
}
```

`deny` абсолютно — ни уровень подтверждения, ни хук, ни память сессии не могут его переопределить. Синтаксис шаблонов, семантика путей и полный список действий — см. [Подтверждения](./agent/approvals.mdx). Проверяйте правила, ничего не запуская: `spirit permission check --shell "git status"`.

Старый `tool-permissions.json` (записывался кнопкой «Всегда доверять») устарел: код больше не читает и не записывает его, автоматической миграции нет. Оставшиеся файлы инертны — удалите их вручную.
