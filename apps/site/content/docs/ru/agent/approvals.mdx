Каждый рискованный вызов инструмента может ожидать вашего подтверждения. У {{product.name|mdx}} есть три уровня подтверждения. Desktop показывает их как **Обычное подтверждение**, **Автоматическое подтверждение** и **Обход подтверждения**. CLI использует `/approval` или `-a`.

| Уровень                      | Id                | Поведение                                                                                                                           |
| ---------------------------- | ----------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Обычное подтверждение        | `default`         | Вы сами подтверждаете изменения файлов, shell и другие высокорисковые инструменты.                                                  |
| Автоматическое подтверждение | `auto-approval`   | Вспомогательная языковая модель проверяет высокорисковые вызовы. Вас не спрашивают, если только эта проверка (или хук) не запросит. |
| Обход подтверждения          | `bypass-approval` | Высокорисковые инструменты работают без запроса подтверждения. Правила `deny` по-прежнему действуют.                                |

## Белый список разрешений

Поверх уровня подтверждения `config.json` может точно задать, что разрешено отдельным командам и путям. Правила находятся в поле верхнего уровня `permission`, сгруппированные по имени инструмента:

```json
{
  "schemaVersion": 2,
  "permission": {
    "shell": {
      "git *": "allow",
      "git push *": "ask",
      "rm -rf *": "deny",
      "sudo *": "deny"
    },
    "read_file": {
      "*": "allow",
      "*/.env*": "ask",
      "~/.ssh/*": "deny"
    }
  }
}
```

Каждый ключ — шаблон, каждое значение — действие:

| Действие | Эффект                                                                                       |
| -------- | -------------------------------------------------------------------------------------------- |
| `allow`  | Запустить без запроса                                                                        |
| `ask`    | Показать запрос на подтверждение                                                             |
| `deny`   | Отказать сразу. Без запроса; модель получает результат с ошибкой инструмента `[denied by permission rule] …` |

Правила `read_file` также покрывают проверки внешних путей в `ls`. Позже могут появиться и другие домены.

### Синтаксис шаблонов

- `*` соответствует нулю или более любых символов, включая `/`. Все остальные символы — литеральные. Никаких `?`, `[]` или `{}`.
- Совпадение строки целиком, с учётом регистра.
- Шаблон, оканчивающийся на `" *"`, совпадает и с самой командой без аргументов: `"git *"` соответствует и `git`, и `git status`.

Порядок правил не важен: любое совпавшее `deny` побеждает, затем `ask`, затем `allow`. Когда ничего не совпало, shell возвращается к `ask` (отказобезопасное поведение). Учтите: запись `"*": "ask"` совпадает со всем и поэтому перекрывает каждое правило `allow` — отказобезопасность и так запрашивает при отсутствии совпадений, поэтому запись `ask` на всё полезна только как документация, а не как запасной вариант.

### deny абсолютно

Правило `deny` нельзя переопределить порядком правил, памятью сессии, хуком, вернувшим `allow`, уровнем `bypass-approval` или вызовом инструмента, который вы запускаете сами.

### Составные shell-команды

{{product.name|mdx}} разбивает shell-команду на простые команды, которые будут выполнены, — с учётом кавычек и экранирования, через `&&`, `||`, `;`, `|`, `|&`, `&`, переводы строк и подоболочки, включая содержимое `$(...)` и обратных кавычек, — и оценивает каждый сегмент. Один запрещённый сегмент запрещает всю команду. Команда, которую {{product.name|mdx}} не может разобрать, на всякий случай запрашивает подтверждение.

### Пути read_file

Шаблоны сопоставляются с каноническим (realpath) абсолютным путём. `~/` в начале раскрывается в ваш домашний каталог. Шаблоны, начинающиеся с `*`, считаются абсолютными: ведущий подстановочный символ поглощает корневой разделитель, поэтому `*` и `"*/.env*"` совпадают с каноническими путями где угодно. Шаблон, начинающийся с литерального относительного сегмента (например, `"src/*.ts"`), имеет семантику относительно рабочей области: он совпадает только с путями внутри текущей рабочей области, никогда с внешними путями, и выдаёт предупреждение lint конфигурации.

Когда ни одно правило не совпало, применяется встроенный запасной вариант по расположению: пути внутри рабочей области и управляемые {{product.name|mdx}} разрешаются, остальные внешние пути запрашивают. Правила могут ужесточать и пути внутри рабочей области — `"*/.env*": "ask"` работает и внутри рабочей области.

Некорректные записи (пустые шаблоны, неизвестные действия, блоки не-объекты) отбрасываются с предупреждениями lint.

## Запоминание подтверждений

Запрос на подтверждение предлагает три варианта:

- **Разрешить один раз** — выполнить только этот вызов.
- **Всегда разрешать** — добавить правило `allow` точного совпадения (дословную команду или канонический путь) в `permission.shell` / `permission.read_file` в config.json. Никакого автоматического вывода шаблонов с подстановкой.
- **Отклонить** — отказать, с необязательным пояснением в свободной форме, которое прочитает модель.

Подтверждения инструментов MCP и встроенного lazy-шлюза одноразовые; запоминание не предлагается. При обычном и автоматическом подтверждении `tool_call` MCP пропускает запрос, только если инструмент объявляет `readOnlyHint: true` и `openWorldHint: false`. Отсутствующие подсказки следуют значениям по умолчанию из спецификации (не read-only, открытый мир) и всё равно запрашивают, как и read-only инструменты с открытым миром и вызовы встроенного lazy-шлюза. По [ACP](../acp.mdx) «всегда разрешать» действует в рамках сессии, а сохранение в config.json недоступно; память сессии никогда не переопределяет правило `deny`.

## Хуки ужесточают, но не смягчают

[Хуки preToolUse](../customize/hooks.mdx) выполняются до оценки белого списка и могут только ужесточать или блокировать. `deny` хука или `deny` белого списка запрещает; `ask` хука или `ask` белого списка запрашивает; хук, вернувший `allow`, не пропускает подтверждение хоста.

## Что обход не пропускает

`bypass-approval` (и вызовы инструментов, которые вы запускаете сами) лишь превращает `ask` в `allow`. Он всё ещё останавливается для:

- Правил `deny` в белом списке
- [ask_questions](./ask-questions.mdx)
- Потоков расширений, которым нужны вопросы
- Хука, который возвращает `ask` на `preToolUse`

Автоматическое подтверждение также не может переопределить хук `ask`.

## Проверка правил офлайн

```bash
spirit permission check --shell "git push origin main"
spirit permission check --read-file ~/.ssh/id_rsa
```

Выводит вердикт, совпавшее правило и детали по каждому сегменту, ничего не запуская. Оценка выполняется на стороне демона, поэтому нужен доступный демон {{product.name|mdx}}.

Интерфейса настроек для правил пока нет. Отредактируйте `config.json` и проверьте командой `spirit permission check`.

## Устарело: tool-permissions.json

<Callout type="warn" title="Устарело">

`tool-permissions.json`, хранилище точных совпадений, которое записывала старая кнопка «Всегда доверять», больше не читается и не записывается. Оставшиеся файлы инертны; удалите их вручную. Автоматической миграции нет — заново создайте нужные вам правила в поле `permission` в `config.json`.

</Callout>

## Когда что использовать

Оставайтесь на **обычном**, пока не увидите, что агент сделал несколько хороших правок. Используйте **автоматическое подтверждение**, когда нужна скорость, но вы всё ещё хотите вторую проверку. Используйте **обход** только на временной ветке или для задачи, за которой вы наблюдаете.

Автономный `spirit -p` завершается с ошибкой, если вызову нужно подтверждение. Передайте `-a auto-approval` или `-a bypass-approval`, либо используйте TUI. Правила с `allow` там тоже выполняются без запроса.
