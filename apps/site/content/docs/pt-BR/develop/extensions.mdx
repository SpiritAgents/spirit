Uma extensão é uma pasta com um `.spirit/extension.json` — o dump de manifesto do Spirit — ao lado de um `package.json` puramente npm. O Spirit instala extensões por usuário e por host, não sob o diretório `.spirit/` do workspace, e delimita cada instalação pelo marketplace de origem: a identidade de instalação é `(id da fonte, name)`.

| Host    | Caminho                                                 |
| ------- | ------------------------------------------------------- |
| Desktop | `{spiritDataDir}/extensions/desktop/<sourceId>/<name>/` |
| CLI     | `{spiritDataDir}/extensions/cli/<sourceId>/<name>/`     |

Isso é diferente de [Skills](../customize/skills.mdx) (pastas `SKILL.md`), [MCP](../customize/mcp.mdx) (servidores externos) e [Hooks](../customize/hooks.mdx) (scripts `hooks.json`). `contributes.cli.hooks` estiliza slots da TUI da CLI. Não é `hooks.json`. Uma extensão ainda pode _empacotar_ esses mesmos arquivos quando declara `mcp`, `hooks`, `skills` ou `rules`.

Cada extensão instalada tem um interruptor de ativação. Desative ou desinstale para interromper suas contribuições. Ligar a extensão é consentimento para executar os servidores MCP, hooks de agente, skills e rules que ela declarou.

O assistente pergunta um nome de extensão (kebab-case), um nome de exibição, uma descrição de uma linha e as capacidades para o scaffold. Ele escreve `package.json`, `icon.svg` e `.spirit/extension.json`, mais os arquivos das capacidades escolhidas (`skills/<name>/SKILL.md`, `rule.md`, `mcp.json`, `hooks.json`, `styles.css`, `index.mjs`), e ao final imprime uma entrada de marketplace pronta para colar.

Para scripting, cada pergunta tem uma flag: `[target-dir]`, `--name`, `--display-name`, `--description`, `--capabilities <csv>` e `--yes` para pular a confirmação.

Valide o resultado a qualquer momento:

```bash
npx @spiritagent/extension-toolkit check ./my-extension
```

Um diretório de extensão precisa de apenas dois arquivos — `.spirit/extension.json` e `package.json` — mais os arquivos das capacidades que declarar:

```text
my-extension/
  .spirit/
    extension.json        # dump de manifesto do Spirit (obrigatório)
  package.json            # puramente npm; apenas `main` é lido
  icon.svg                # opcional; apenas SVG, sem <script>
  index.mjs               # opcional; a entrada de activate referenciada por `main`
  mcp.json                # ao declarar mcp
  hooks.json              # ao declarar hooks (hooks de agente)
  rule.md                 # ao declarar rules
  skills/<name>/SKILL.md  # ao declarar skills
  styles.css              # ao declarar CSS de desktop (caminho referenciado no manifesto)
  cli-hooks.json          # ao declarar hooks de CLI (caminho referenciado no manifesto)
```

`package.json` não carrega nenhum campo do Spirit — `name`, `version`, `description`, `author`, `homepage`, `license`, `main`, `keywords` permanecem puramente npm. O host lê apenas `main`, a entrada de módulo de [`activate`](#activate).

Campos do `.spirit/extension.json`:

| Campo           | Descrição                                                                                                                                                           |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schemaVersion` | Obrigatório. Deve ser `1`                                                                                                                                           |
| `name`          | Obrigatório. kebab-case; o id da entrada dentro de um marketplace                                                                                                   |
| `version`       | Obrigatório. Semver `major.minor.patch`; sufixos de pré-lançamento não são suportados                                                                               |
| `sourceId`      | Obrigatório. Id da fonte do marketplace proprietário. Pacotes ZIP autodeclaram qualquer valor (por exemplo `"self-declared"`); o pipeline de instalação o reescreve |
| `displayName`   | Obrigatório. Nome visível ao usuário                                                                                                                                |
| `description`   | Obrigatório. Resumo de uma linha                                                                                                                                    |
| `icon`          | Opcional. Caminho SVG relativo à raiz da extensão                                                                                                                   |
| `author`        | Opcional. `{ name, email?, url? }` ou uma string no estilo npm `"Name <email> (url)"`                                                                               |
| `category`      | Opcional. String única                                                                                                                                              |
| `keywords`      | Opcional. Matriz de strings de palavras-chave de busca                                                                                                              |
| `homepage`      | Opcional. URL do projeto                                                                                                                                            |
| `manifest`      | Obrigatório. A declaração de runtime — veja a seção «O `manifest`»                                                                                                  |

O dump não carrega `source` nem campos de curadoria (`reviewStatus`, `featured`) — esses pertencem à entrada do marketplace.

Arquivos declarados devem existir e ser válidos: declarar `mcp`, `hooks`, `skills` ou `rules` sem o arquivo correspondente falha na validação e na instalação. Arquivos presentes mas não declarados são ignorados e nunca carregados.

## O `manifest`

O objeto `manifest` é a declaração de runtime da extensão: quais hosts ela suporta, quando ela ativa e o que ela contribui. Numa entrada de marketplace, o manifesto é endossado pelo operador do marketplace; num pacote ZIP, é autodeclarado e controlado pela confirmação de revisão.

### Capacidades

| Valor                | Runtime                                                                              |
| -------------------- | ------------------------------------------------------------------------------------ |
| `tool-definitions`   | Necessário com `tool-execution` para expor `contributes.tools` ao modelo             |
| `tool-execution`     | Necessário com `tool-definitions` para executar essas ferramentas                    |
| `system-prompt`      | Necessário com `main` para contribuir com um fragmento de prompt de sistema          |
| `desktop-ui`         | Deve ser emparelhado com `contributes.desktop`                                       |
| `cli-ui`             | Deve ser emparelhado com `contributes.cli`                                           |
| `mcp`                | Deve ser emparelhado com `contributes.mcp`; carrega `mcp.json` na raiz do pacote     |
| `hooks`              | Deve ser emparelhado com `contributes.hooks`; carrega `hooks.json` na raiz do pacote |
| `skills`             | Deve ser emparelhado com `contributes.skills`; carrega `skills/<name>/SKILL.md`      |
| `rules`              | Deve ser emparelhado com `contributes.rules`; carrega `rule.md` na raiz do pacote    |
| `approval-flow`      | Somente declarado. A aprovação é conduzida pelo `approvalMode` de cada ferramenta    |
| `questions-flow`     | Somente declarado. As perguntas são conduzidas por `approvalMode: need-questions`    |
| `settings`           | Somente declarado. As configurações vêm de `settingsSchema`                          |
| `secret-storage`     | Usado com `secretSlots`                                                              |
| `structured-results` | Somente declarado                                                                    |

`desktop-ui` / `cli-ui` / `mcp` / `hooks` / `skills` / `rules` e a entrada `contributes` correspondente devem estar ambos presentes ou ambos ausentes.

### Eventos de ativação

| Evento                 | Quando dispara                              |
| ---------------------- | ------------------------------------------- |
| `onStartup`            | Aquecimento do host                         |
| `onExtensionInstalled` | Após a conclusão de uma instalação          |
| `onSessionOpened`      | Sessão se torna ativa                       |
| `onSessionReset`       | Reset da sessão                             |
| `onUserMessage`        | Usuário envia uma mensagem                  |
| `onToolCall`           | Uma ferramenta está prestes a ser executada |
| `onToolResult`         | Um resultado de ferramenta está disponível  |
| `onApprovalResolved`   | Uma decisão de aprovação é resolvida        |

O host chama `activate` quando a extensão lista o evento e tem um `main` legível.

### `contributes.tools`

| Campo           | Descrição                                                |
| --------------- | -------------------------------------------------------- |
| `name`          | Obrigatório. `[a-z0-9]+(?:[._-][a-z0-9]+)*`              |
| `description`   | Obrigatório. Mostrado ao modelo                          |
| `inputSchema`   | Obrigatório. Objeto JSON Schema                          |
| `outputSchema`  | Opcional. Objeto JSON Schema                             |
| `approvalMode`  | Opcional. `allowed`, `need-approval` ou `need-questions` |
| `executionMode` | Opcional. `foreground` ou `background`                   |

O modelo não vê `name` como está. O host constrói um nome de invocação como `extension__{id}__{tool}__{hash}`.

### `contributes.desktop`

Requer `desktop-ui`.

| Campo          | Descrição                                                                                |
| -------------- | ---------------------------------------------------------------------------------------- |
| `css[].path`   | Obrigatório. Arquivo CSS relativo à raiz do pacote                                       |
| `css[].media`  | Opcional. Media query CSS                                                                |
| `settingsPage` | Opcional. `true`, `{}` ou `{ title }` — adiciona uma entrada de configurações no Desktop |
| `views[].id`   | Obrigatório. kebab-case, exclusivo na extensão |
| `views[].path` | Obrigatório. ESM pré-compilado em um único arquivo (`.js` / `.mjs`) relativo à raiz do pacote. O host não compila TSX. Imports relativos retornam 404 — o protocolo serve só este arquivo. |
| `views[].title` | Opcional. Título do diálogo |
| `views[].width` | Opcional. Largura do diálogo |
| `views[].height` | Opcional. Altura do diálogo |
| `views[].chrome` | Opcional. Chrome do diálogo: `default` (título + fechar), `close-only` (ocultar título, manter fechar) ou `none` (ocultar ambos). Omitir equivale a `default`. |

Exportação padrão: `export default function View({ params, close })`. `close(result)` encerra a view. O host injeta React e `@spirit/desktop-ui`.

### `contributes.cli`

Requer `cli-ui`. `hooks` é um objeto com `path`, não um array inline:

```json
{
  "hooks": { "path": "cli-hooks.json" }
}
```

O arquivo deve ser `{ "hooks": [ ... ] }`.

| Campo     | Descrição                                                                |
| --------- | ------------------------------------------------------------------------ |
| `slot`    | Obrigatório. Um dos slots abaixo                                         |
| `variant` | Opcional. `default`, `accented`, `muted`, `warning`, `success`, `danger` |
| `tokens`  | Opcional. `{ foreground?, border?, accent? }`                            |
| `prefix`  | Opcional. String                                                         |
| `suffix`  | Opcional. String                                                         |

Slots: `message.user`, `message.assistant`, `message.tool`, `assistant.thinking`, `input.frame`, `bottom_form`, `bottom_form.section`, `slash_suggestions`, `approval.panel`, `questions.panel`.

Papéis de token: `default`, `primary`, `secondary`, `muted`, `accent`, `success`, `warning`, `danger`.

```json
{
  "hooks": [
    {
      "slot": "input.frame",
      "variant": "accented",
      "tokens": { "border": "accent" },
      "prefix": "[",
      "suffix": "]"
    }
  ]
}
```

### MCP, hooks, skills e rules empacotados

Exigem a capability correspondente. `contributes.mcp`, `contributes.hooks`, `contributes.skills` e `contributes.rules` são `true` ou `{}`. Os caminhos são convencionais; caminhos personalizados não são permitidos.

| Contribuição | Capability | Arquivo                                                                                          |
| ------------ | ---------- | ------------------------------------------------------------------------------------------------ |
| MCP          | `mcp`      | `mcp.json` na raiz do pacote (mesmo schema do MCP de usuário/workspace)                          |
| Agent hooks  | `hooks`    | `hooks.json` na raiz do pacote (mesmo schema dos hooks do agente; não é `contributes.cli.hooks`) |
| Skills       | `skills`   | `skills/<name>/SKILL.md`                                                                         |
| Rules        | `rules`    | `rule.md` na raiz do pacote                                                                      |

Declarado mas ausente ou inválido: a instalação falha. Arquivos não declarados são ignorados e nunca carregados.

`command` e `cwd` relativos são resolvidos em relação à raiz da extensão. Se um MCP stdio omitir `cwd`, o padrão é a raiz da extensão.

Essas contribuições entram na sessão em runtime quando a extensão está ativada. Não aparecem em **Configurações → MCPs | Hooks | Skills | Rules**. Em conflito de nome: workspace > usuário > extensão.

Durante `tools/call`, um MCP empacotado pode enviar `spirit/ui/open` (`{ viewId, params }`) se o cliente declarou `experimental["spirit/ui"]`. O Spirit só abre uma view da mesma extensão em `contributes.desktop.views`. MCP de usuário/workspace é recusado. O diálogo bloqueia essa chamada; `close(result)` volta na mesma requisição. Hosts sem janela respondem `{ "kind": "unavailable", "reason": "host-has-no-ui" }` e a ferramenta deve degradar.

### `settingsSchema`

| Campo          | Descrição                                                             |
| -------------- | --------------------------------------------------------------------- |
| `key`          | Obrigatório. Mesmo padrão dos nomes de ferramentas                    |
| `type`         | Obrigatório. `string`, `boolean`, `number` ou `select`                |
| `title`        | Obrigatório. Rótulo da interface                                      |
| `description`  | Opcional                                                              |
| `placeholder`  | Opcional                                                              |
| `required`     | Opcional. Booleano                                                    |
| `defaultValue` | Opcional. Deve corresponder ao `type`                                 |
| `options`      | Obrigatório para `select`. Matriz de `{ value, label, description? }` |

Os valores são `string`, `number`, `boolean` ou `null`. `null` limpa uma configuração não obrigatória.

### `secretSlots`

| Campo         | Descrição          |
| ------------- | ------------------ |
| `key`         | Obrigatório        |
| `title`       | Obrigatório        |
| `description` | Opcional           |
| `required`    | Opcional. Booleano |

Desktop armazena segredos no chaveiro do sistema operacional. No caminho do daemon CLI, `secrets.set` / `secrets.delete` pode não estar disponível.

## `activate`

`main` é carregado com `import` dinâmico. Exporte um dos seguintes:

- `export function activate(ctx) { ... }`
- `export default function activate(ctx) { ... }`
- `export default { activate }`

### `ctx`

| Campo             | Descrição                                                                                                  |
| ----------------- | ---------------------------------------------------------------------------------------------------------- |
| `extension`       | `{ id, name, version, directoryPath, manifestPath, main }`                                                 |
| `host`            | API do host. Desktop implementa `showMessageBox` e `ui.open` / `ui.close`. CLI é `{}`                       |
| `log`             | `(message: string) => void`                                                                                |
| `settings`        | `get(key)`, `getAll()`, `set(key, value)`, `setAll(values)`                                                |
| `secrets`         | `get(key)`, `has(key)`, `set(key, value)`, `delete(key)` — as chaves devem ser declaradas em `secretSlots` |
| `activationEvent` | Opcional. `{ type, detail? }`                                                                              |

### Valor de retorno

Retorne um objeto, ou exporte os mesmos campos do módulo.

| Campo             | Descrição                                                                           |
| ----------------- | ----------------------------------------------------------------------------------- |
| `tools`           | `Record<string, (ctx) => unknown>`. As chaves são nomes de ferramentas do manifesto |
| `invokeTool`      | `(ctx) => unknown`. Usado no lugar de `tools[name]` quando presente                 |
| `systemPrompt`    | Fragmento de sistema estático                                                       |
| `getSystemPrompt` | `() => string \| Promise<string>`. Usado no lugar de `systemPrompt` quando presente |
| `onEvent`         | `(event) => void`                                                                   |
| `dispose`         | `() => void`. Chamado na remoção ou recarga                                         |

### Manipulador de ferramenta `ctx`

| Campo             | Descrição                                                   |
| ----------------- | ----------------------------------------------------------- |
| `extension`       | Mesma informação de tempo de execução que `activate`        |
| `host`            | Mesma API do host                                           |
| `toolName`        | Nome da ferramenta no manifesto                             |
| `arguments`       | Objeto do modelo                                            |
| `log`             | Mesmo logger                                                |
| `settings`        | Mesmo acessador de configurações                            |
| `secrets`         | Mesmo acessador de segredos                                 |
| `toolCallId`      | Opcional                                                    |
| `questionsResult` | Opcional. Definido quando `approvalMode` é `need-questions` |

Um resultado `string` é repassado. Outros valores são `JSON.stringify(value, null, 2)`. `undefined` vira `""`.

### `host.showMessageBox` no Desktop

| Campo       | Descrição                                                |
| ----------- | -------------------------------------------------------- |
| `title`     | Obrigatório. String                                      |
| `message`   | Obrigatório. String                                      |
| `detail`    | Opcional. String                                         |
| `buttons`   | Opcional. Matriz de strings                              |
| `cancelId`  | Opcional. Número                                         |
| `defaultId` | Opcional. Número                                         |
| `noLink`    | Opcional. Booleano                                       |
| `type`      | Opcional. `none`, `info`, `error`, `question`, `warning` |

```js
export function activate(ctx) {
  return {
    systemPrompt: "Use lookup_item when the user asks for an item by id.",
    async invokeTool({ toolName, arguments: args, settings, secrets }) {
      if (toolName !== "lookup_item") {
        throw new Error(`Unknown tool: ${toolName}`);
      }
      const region = await settings.get("region");
      const token = await secrets.get("api_token");
      return { id: args.id, region, hasToken: Boolean(token) };
    },
    dispose() {
      ctx.log("example-extension disposed");
    },
  };
}
```

## Distribuir como ZIP

Empacote um diretório de extensão no formato ZIP compartilhável (conteúdo mais `.spirit/extension.json`):

```bash
npx @spiritagent/extension-toolkit pack ./my-extension
```

O comando valida o pacote primeiro e escreve `<name>-<version>.zip` no diretório atual. Os usuários importam o ZIP na página **Extensões** ou com `spirit extension import`; ele chega ao marketplace Pessoal deles. Veja [Extensões](../customize/extensions.mdx).

Para listar a extensão em um marketplace, veja [Publicar com publish](#publicar-com-publish).

## Operar um marketplace de extensões remoto

Um marketplace de extensões remoto é um diretório servível com um índice `.spirit/marketplace.json`: um repositório Git, um site estático ou um diretório local. Os usuários o adicionam com `spirit extension marketplace add <url|path>` ou na página **Extensões** do Desktop, e então navegam e instalam suas entradas.

<Tabs items={["Repositório de modelo", "Manual"]}>
<Tab value="Repositório de modelo">

[Use this template](https://github.com/new?template_owner=SpiritAgents&template_name=extension-template) cria seu próprio repositório de marketplace a partir de `SpiritAgents/extension-template`.

O modelo traz o layout de registro, duas extensões de exemplo e CI que valida o registro em cada push e pull request. Para publicar uma extensão:

1. Crie o scaffold com `npm create @spiritagent/extension`.
2. Execute `npx @spiritagent/extension-toolkit publish ./my-extension /path/to/your-marketplace-clone` — ele copia a extensão para `extensions/` e mescla a entrada em `.spirit/marketplace.json`. Veja [Publicar com publish](#publicar-com-publish).
3. Faça push — os usuários adicionam o marketplace pela sua URL Git.

</Tab>
<Tab value="Manual">

Uma raiz de marketplace contém o índice mais um diretório de conteúdo por extensão:

```text
my-marketplace/
  .spirit/
    marketplace.json  # o índice
  extensions/
    my-extension/     # diretório de conteúdo (pacote npm simples + arquivos de capacidades)
      icon.svg
      package.json
      ...
```

Caminhos relativos dentro do `marketplace.json` resolvem contra a raiz do marketplace e não devem conter segmentos `..` nem caminhos absolutos.

Campos da entrada, por grupo:

- **Identidade** — `name` (kebab-case; o id da entrada), `version` (semver, sem pré-lançamento) e `source`: uma string de caminho relativo à raiz como `"./extensions/my-extension"` para conteúdo local, ou `{ "source": "npm", "package": "@scope/name@1.0.0" }` para fixar uma versão npm exata (a integridade é verificada contra o hash SRI do packument na instalação).
- **Exibição** — `displayName`, `description`, `icon` (caminho SVG relativo à raiz), `category`, `keywords`, `homepage`, `author`.
- **Declaração** — `manifest`: a declaração de runtime descrita na seção «O `manifest`». O marketplace a endossa; um pacote não pode afirmar capacidades por conta própria.
- **Curadoria** — `featured` e `reviewStatus` (`unverified` / `verified` / `revoked`).

O `extension-toolkit publish` pode mesclar a entrada para você — veja [Publicar com publish](#publicar-com-publish).

Valide o registro localmente — offline: schema, nomes kebab-case, semver sem pré-lançamento, formato de fontes npm, arquivos de contribuição declarados para fontes locais e regras de ícone:

```bash
npx -y @spiritagent/extension-toolkit marketplace check .
```

Disciplina de revisão: pull requests que adicionam uma entrada ou mudam sua `version` devem manter `reviewStatus: "unverified"`; a promoção para `verified` acontece em um commit separado após revisão humana. O `.github/workflows/marketplace.yml` do repositório de modelo é uma implementação de referência — ele compara o índice contra a base do PR.

</Tab>
</Tabs>

### Marketplaces locais

Qualquer diretório local com um `.spirit/marketplace.json` funciona como marketplace — adicione-o com `spirit extension marketplace add <path>` ou em **Adicionar do disco** no Desktop. Marketplaces locais são lidos no lugar e não precisam de CI, o que os torna o loop de desenvolvimento dos autores de extensões: editar, reinstalar, repetir.

### Publicar com publish

O `extension-toolkit publish` mescla o `.spirit/extension.json` de uma extensão no `.spirit/marketplace.json` de um marketplace e copia o conteúdo que a fonte da entrada precisa:

```bash
npx @spiritagent/extension-toolkit publish ./my-extension ./my-marketplace
```

- O primeiro argumento é o diretório da extensão; o segundo é a raiz do marketplace — qualquer diretório local com um `.spirit/marketplace.json`: um clone do repositório de modelo, o marketplace Pessoal em `{spiritDataDir}/marketplaces/personal`, e assim por diante.
- `--source local` (padrão): copia o pacote completo para `extensions/<name>/` do marketplace — incluindo `.spirit/extension.json`, excluindo `node_modules` e `.git` — e aponta o `source` da entrada para ele.
- `--source npm`: fixa `name@version` a partir do `package.json` da extensão como o `source` npm da entrada; apenas o ícone declarado é copiado para `extensions/<name>/` (marketplaces hospedam os próprios ícones). A publicação do pacote npm em si continua com a sua CLI npm.
- `--dry-run`: imprime a entrada e as ações planejadas sem escrever nada.
- Regras de mesclagem: uma entrada com o mesmo nome é substituída no lugar; caso contrário, é adicionada. Entradas novas e mudanças de `version` voltam para `reviewStatus: "unverified"`; republicar a mesma versão a mantém. Campos de curadoria como `featured` sempre mantêm os valores do marketplace.
- A mesma validação do `check` roda primeiro; em caso de falha, nada é escrito.
