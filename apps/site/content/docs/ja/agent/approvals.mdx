すべてのリスクのあるツール呼び出しはあなたを待つことができます。{{product.name|mdx}} には3つの承認レベルがあります。Desktop では **デフォルト承認**、**自動承認**、**バイパス承認** として表示されます。CLI では `/approval` または `-a` を使用します。

| レベル         | ID                | 動作                                                                                                                                 |
| -------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| デフォルト承認 | `default`         | ファイル編集、シェル、その他の高リスクツールは自分で承認します。                                                                     |
| 自動承認       | `auto-approval`   | セカンダリ言語モデルが高リスクな呼び出しをレビューします。そのレビュー（またはフック）が要求しない限り、プロンプトは表示されません。 |
| バイパス承認   | `bypass-approval` | 高リスクツールは承認プロンプトなしで実行されます。`deny` ルールは引き続き適用されます。                                              |

## 許可リスト

承認レベルに加えて、`config.json` で個々のコマンドやパスが何をしてよいかを細かく定められます。ルールはトップレベルの `permission` フィールドの下に、ツール名でグループ化して配置します：

```json
{
  "schemaVersion": 2,
  "permission": {
    "shell": {
      "git *": "allow",
      "git push *": "ask",
      "rm -rf *": "deny",
      "sudo *": "deny"
    },
    "read_file": {
      "*": "allow",
      "*/.env*": "ask",
      "~/.ssh/*": "deny"
    }
  }
}
```

各キーはパターン、各値はアクションです：

| アクション | 効果                                                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------------------------ |
| `allow`    | プロンプトなしで実行します                                                                                               |
| `ask`      | 承認プロンプトを表示します                                                                                               |
| `deny`     | 即座に拒否します。プロンプトは表示されず、モデルには `[denied by permission rule] …` というツール失敗の結果が返されます |

`read_file` のルールは `ls` の外部パスチェックにも適用されます。今後、対象ドメインが増える可能性があります。

### パターン構文

- `*` は `/` を含む任意の文字の0文字以上にマッチします。それ以外の文字はすべてリテラルです。`?`、`[]`、`{}` はありません。
- 文字列全体に対するマッチで、大文字と小文字を区別します。
- `" *"` で終わるパターンは、引数なしのコマンドにもマッチします：`"git *"` は `git` と `git status` の両方にマッチします。

ルールの順序は関係ありません：マッチした `deny` が優先され、次に `ask`、最後に `allow` です。何もマッチしない場合、シェルは `ask` にフォールバックします（フェイルセーフ）。`"*": "ask"` エントリはすべてにマッチするため、すべての `allow` ルールを上回ることに注意してください。フェイルセーフはマッチしない場合にすでに確認を求めるため、全マッチの `ask` エントリはフォールバックとしてではなく、ドキュメントとしてのみ有用です。

### deny は絶対です

`deny` ルールは、ルールの順序、セッションメモリ、`allow` を返すフック、`bypass-approval` レベル、自分で開始したツール実行のいずれによっても上書きできません。

### 複合シェルコマンド

{{product.name|mdx}} はシェルコマンドを、実際に実行される単純なコマンドに分割します。クォートとエスケープを尊重し、`&&`、`||`、`;`、`|`、`|&`、`&`、改行、サブシェル、`$(...)` やバッククォートの内容をまたいで分割し、各セグメントを評価します。1つでも拒否されたセグメントがあれば、コマンド全体が拒否されます。{{product.name|mdx}} が解析できないコマンドは、安全側に倒して確認を求めます。

### read_file のパス

パターンは正規化された（realpath）絶対パスにマッチします。先頭の `~/` はホームディレクトリに展開されます。`*` で始まるパターンは絶対パスとして扱われます。先頭のワイルドカードがルートセパレーターを吸収するため、`*` と `"*/.env*"` は任意の場所の正規パスにマッチします。リテラルの相対セグメントで始まるパターン（例：`"src/*.ts"`）はワークスペース相対の意味を持ち、現在のワークスペース内のパスにのみマッチし、外部のパスには決してマッチせず、設定の lint 警告が出力されます。

ルールにマッチしない場合、組み込みのロケーションフォールバックが適用されます：ワークスペース内部と {{product.name|mdx}} が管理するパスは allow、その他の外部パスは ask になります。ルールでワークスペース内部のパスを厳しくすることもできます。`"*/.env*": "ask"` はワークスペース内でも機能します。

無効なエントリ（空のパターン、未知のアクション、オブジェクトでないブロック）は lint 警告とともに破棄されます。

## 承認の記憶

承認プロンプトには3つの選択肢があります：

- **Allow once** — この呼び出しのみ実行します。
- **Always Allow** — config.json の `permission.shell` / `permission.read_file` に完全一致の `allow` ルール（入力されたコマンドまたは正規パスそのまま）を追加します。ワイルドカードの推測は行いません。
- **Deny** — 拒否します。モデルが読む任意の自由テキストの指示を添えられます。

MCP と組み込み lazy-gateway のツール承認は一回限りで、記憶の選択肢は提供されません。デフォルト承認と自動承認では、MCP の `tool_call` はツールが `readOnlyHint: true` と `openWorldHint: false` を宣言している場合にのみプロンプトをスキップします。ヒントが欠けている場合は仕様のデフォルト（読み取り専用ではない、オープンワールド）に従って引き続き確認を求めます。オープンワールドの読み取り専用ツールと組み込み lazy-gateway の呼び出しも同様です。[ACP](../acp.mdx) 経由では、「allow always」はセッションスコープであり、config.json への永続化は公開されていません。セッションメモリが `deny` ルールを上書きすることはありません。

## フックは厳しくするだけで、緩めることはありません

[preToolUse フック](../customize/hooks.mdx) は許可リストの評価より前に実行され、厳しくすることとブロックのみが可能です。フックの `deny` または許可リストの `deny` は拒否し、フックの `ask` または許可リストの `ask` は確認を求めます。`allow` を返すフックはホストの承認をスキップしません。

## バイパスがスキップしないもの

`bypass-approval` でも以下は停止します：

- 許可リストの `deny` ルール
- [ask_questions](./ask-questions.mdx)
- 質問が必要な拡張機能フロー
- `preToolUse` で `ask` を返すフック

自動承認もフックの `ask` を上書きできません。

## ルールをオフラインでテストする

```bash
spirit permission check --shell "git push origin main"
spirit permission check --read-file ~/.ssh/id_rsa
```

何も実行せずに、判定、マッチしたルール、セグメントごとの詳細を出力します。評価はデーモン側で実行されるため、接続可能な {{product.name|mdx}} デーモンが必要です。

ルール用の設定 UI はまだありません。`config.json` を編集し、`spirit permission check` で確認してください。

## 非推奨：tool-permissions.json

<Callout type="warn" title="非推奨">

`tool-permissions.json`（古い「Always Trust」ボタンが書き込んでいた完全一致のストア）は、読み取りも書き込みもされなくなりました。残っているファイルは動作に影響しないため、手動で削除してください。自動移行はありません。必要なルールは `config.json` の `permission` の下に再作成してください。

</Callout>

## どれを使うべきか

エージェントがいくつか良い編集を行うのを見るまで **デフォルト** のままにしてください。スピードが欲しいが、それでも二重チェックが必要な場合は **自動承認** を使用してください。**バイパス** は、捨てるブランチまたは監視しているタスクでのみ使用してください。

ヘッドレス `spirit -p` は、呼び出しが承認を必要とする場合に失敗します。`-a auto-approval` または `-a bypass-approval` を渡すか、TUI を使用してください。`allow` のルールはそこでもプロンプトなしで実行されます。
