Une extension est un dossier contenant un `.spirit/extension.json` — le dump de manifeste Spirit — à côté d'un `package.json` purement npm. Spirit installe les extensions par utilisateur et par hôte, pas sous le répertoire `.spirit/` de l'espace de travail, et isole chaque installation selon le marché d'origine : l'identité d'installation est `(id de source, name)`.

| Hôte    | Chemin                                                  |
| ------- | ------------------------------------------------------- |
| Desktop | `{spiritDataDir}/extensions/desktop/<sourceId>/<name>/` |
| CLI     | `{spiritDataDir}/extensions/cli/<sourceId>/<name>/`     |

Cela diffère des [Skills](../customize/skills.mdx) (dossiers `SKILL.md`), de [MCP](../customize/mcp.mdx) (serveurs externes) et des [Hooks](../customize/hooks.mdx) (scripts `hooks.json`). `contributes.cli.hooks` stylise les emplacements de la TUI CLI. Ce n'est pas `hooks.json`. Une extension peut néanmoins _regrouper_ ces mêmes fichiers lorsqu'elle déclare `mcp`, `hooks`, `skills` ou `rules`.

Chaque extension installée possède un interrupteur d'activation. Désactivez-la ou désinstallez-la pour arrêter ses contributions. Activer l'extension vaut consentement à exécuter les serveurs MCP, hooks d'agent, skills et rules qu'elle déclare.

L'assistant demande un nom d'extension (kebab-case), un nom d'affichage, une description d'une ligne et les capacités à générer. Il écrit `package.json`, `icon.svg` et `.spirit/extension.json`, plus les fichiers des capacités choisies (`skills/<name>/SKILL.md`, `rule.md`, `mcp.json`, `hooks.json`, `styles.css`, `index.mjs`), et affiche en terminant une entrée de marché prête à coller.

Pour les scripts, chaque question a un drapeau : `[target-dir]`, `--name`, `--display-name`, `--description`, `--capabilities <csv>`, et `--yes` pour sauter la confirmation.

Validez le résultat à tout moment :

```bash
npx @spiritagent/extension-toolkit check ./my-extension
```

Un répertoire d'extension n'a besoin que de deux fichiers — `.spirit/extension.json` et `package.json` — plus les fichiers des capacités déclarées :

```text
my-extension/
  .spirit/
    extension.json        # dump de manifeste Spirit (obligatoire)
  package.json            # purement npm ; seul `main` est lu
  icon.svg                # facultatif ; SVG uniquement, pas de <script>
  index.mjs               # facultatif ; l'entrée activate référencée par `main`
  mcp.json                # lorsque mcp est déclaré
  hooks.json              # lorsque hooks est déclaré (hooks d'agent)
  rule.md                 # lorsque rules est déclaré
  skills/<name>/SKILL.md  # lorsque skills est déclaré
  styles.css              # lorsque le CSS desktop est déclaré (chemin référencé depuis le manifeste)
  cli-hooks.json          # lorsque les hooks CLI sont déclarés (chemin référencé depuis le manifeste)
```

`package.json` ne porte aucun champ Spirit — `name`, `version`, `description`, `author`, `homepage`, `license`, `main`, `keywords` restent purement npm. L'hôte ne lit que `main`, l'entrée de module d'[`activate`](#activate).

Champs de `.spirit/extension.json` :

| Champ           | Description                                                                                                                                                                         |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schemaVersion` | Obligatoire. Doit valoir `1`                                                                                                                                                        |
| `name`          | Obligatoire. kebab-case ; l'id d'entrée au sein d'un marché                                                                                                                         |
| `version`       | Obligatoire. Semver `major.minor.patch` ; les suffixes de pré-version ne sont pas pris en charge                                                                                    |
| `sourceId`      | Obligatoire. Id de la source du marché propriétaire. Les paquets ZIP auto-déclarent n'importe quelle valeur (par exemple `"self-declared"`) ; le pipeline d'installation la réécrit |
| `displayName`   | Obligatoire. Nom visible par l'utilisateur                                                                                                                                          |
| `description`   | Obligatoire. Résumé d'une ligne                                                                                                                                                     |
| `icon`          | Facultatif. Chemin SVG relatif à la racine de l'extension                                                                                                                           |
| `author`        | Facultatif. `{ name, email?, url? }` ou une chaîne de style npm `"Name <email> (url)"`                                                                                              |
| `category`      | Facultatif. Chaîne unique                                                                                                                                                           |
| `keywords`      | Facultatif. Tableau de chaînes de mots-clés de recherche                                                                                                                            |
| `manifest`      | Obligatoire. La déclaration d'exécution — voir la section « Le `manifest` »                                                                                                         |

Le dump ne porte ni `source` ni champs de curation (`reviewStatus`, `featured`) — ceux-ci appartiennent à l'entrée du marché.

Les fichiers déclarés doivent exister et être valides : déclarer `mcp`, `hooks`, `skills` ou `rules` sans le fichier correspondant fait échouer la validation et l'installation. Les fichiers présents mais non déclarés sont ignorés et jamais chargés.

</Tab>
</Tabs>

## Le `manifest`

L'objet `manifest` est la déclaration d'exécution de l'extension : quels hôtes elle prend en charge, quand elle s'active et ce qu'elle contribue. Dans une entrée de marché, le manifeste est cautionné par l'opérateur du marché ; dans un paquet ZIP, il est auto-déclaré et encadré par la confirmation de vérification.

### Capacités

| Valeur               | Runtime                                                                             |
| -------------------- | ----------------------------------------------------------------------------------- |
| `tool-definitions`   | Requis avec `tool-execution` pour exposer `contributes.tools` au modèle             |
| `tool-execution`     | Requis avec `tool-definitions` pour exécuter ces outils                             |
| `system-prompt`      | Requis avec `main` pour contribuer un fragment de prompt système                    |
| `desktop-ui`         | Doit être associé à `contributes.desktop`                                           |
| `cli-ui`             | Doit être associé à `contributes.cli`                                               |
| `mcp`                | Doit être associé à `contributes.mcp` ; charge `mcp.json` à la racine du paquet     |
| `hooks`              | Doit être associé à `contributes.hooks` ; charge `hooks.json` à la racine du paquet |
| `skills`             | Doit être associé à `contributes.skills` ; charge `skills/<name>/SKILL.md`          |
| `rules`              | Doit être associé à `contributes.rules` ; charge `rule.md` à la racine du paquet    |
| `approval-flow`      | Déclaré uniquement. L'approbation est pilotée par `approvalMode` de chaque outil    |
| `questions-flow`     | Déclaré uniquement. Les questions sont pilotées par `approvalMode: need-questions`  |
| `settings`           | Déclaré uniquement. Les paramètres proviennent de `settingsSchema`                  |
| `secret-storage`     | Utilisé avec `secretSlots`                                                          |
| `structured-results` | Déclaré uniquement                                                                  |

`desktop-ui` / `cli-ui` / `mcp` / `hooks` / `skills` / `rules` et l'entrée `contributes` correspondante doivent être tous deux présents ou tous deux absents.

### Événements d'activation

| Événement              | Moment de déclenchement                 |
| ---------------------- | --------------------------------------- |
| `onStartup`            | Échauffement de l'hôte                  |
| `onExtensionInstalled` | Une fois l'installation terminée        |
| `onSessionOpened`      | La session devient active               |
| `onSessionReset`       | Réinitialisation de la session          |
| `onUserMessage`        | L'utilisateur soumet un message         |
| `onToolCall`           | Un outil est sur le point de s'exécuter |
| `onToolResult`         | Un résultat d'outil est disponible      |
| `onApprovalResolved`   | Une décision d'approbation est résolue  |

L'hôte appelle `activate` lorsque l'extension répertorie l'événement et possède un `main` lisible.

### `contributes.tools`

| Champ           | Description                                                |
| --------------- | ---------------------------------------------------------- |
| `name`          | Obligatoire. `[a-z0-9]+(?:[._-][a-z0-9]+)*`                |
| `description`   | Obligatoire. Affiché au modèle                             |
| `inputSchema`   | Obligatoire. Objet JSON Schema                             |
| `outputSchema`  | Facultatif. Objet JSON Schema                              |
| `approvalMode`  | Facultatif. `allowed`, `need-approval` ou `need-questions` |
| `executionMode` | Facultatif. `foreground` ou `background`                   |

Le modèle ne voit pas `name` tel quel. L'hôte construit un nom d'invocation comme `extension__{id}__{tool}__{hash}`.

### `contributes.desktop`

Requiert `desktop-ui`.

| Champ          | Description                                                                       |
| -------------- | --------------------------------------------------------------------------------- |
| `css[].path`   | Obligatoire. Fichier CSS relatif à la racine du package                           |
| `css[].media`  | Facultatif. Requête média CSS                                                     |
| `settingsPage` | Facultatif. `true`, `{}` ou `{ title }` — ajoute une entrée de paramètres Desktop |

### `contributes.cli`

Requiert `cli-ui`. `hooks` est un objet avec `path`, pas un tableau en ligne :

```json
{
  "hooks": { "path": "cli-hooks.json" }
}
```

Le fichier doit être `{ "hooks": [ ... ] }`.

| Champ     | Description                                                               |
| --------- | ------------------------------------------------------------------------- |
| `slot`    | Requis. L'un des emplacements ci-dessous                                  |
| `variant` | Optionnel. `default`, `accented`, `muted`, `warning`, `success`, `danger` |
| `tokens`  | Optionnel. `{ foreground?, border?, accent? }`                            |
| `prefix`  | Optionnel. Chaîne de caractères                                           |
| `suffix`  | Optionnel. Chaîne de caractères                                           |

Emplacements : `message.user`, `message.assistant`, `message.tool`, `assistant.thinking`, `input.frame`, `bottom_form`, `bottom_form.section`, `slash_suggestions`, `approval.panel`, `questions.panel`.

Rôles de jeton : `default`, `primary`, `secondary`, `muted`, `accent`, `success`, `warning`, `danger`.

```json
{
  "hooks": [
    {
      "slot": "input.frame",
      "variant": "accented",
      "tokens": { "border": "accent" },
      "prefix": "[",
      "suffix": "]"
    }
  ]
}
```

### MCP, hooks, skills et rules bundlés

Exigent la capability correspondante. `contributes.mcp`, `contributes.hooks`, `contributes.skills` et `contributes.rules` valent `true` ou `{}`. Les chemins sont conventionnels ; les chemins personnalisés ne sont pas autorisés.

| Contribution | Capability | Fichier                                                                                            |
| ------------ | ---------- | -------------------------------------------------------------------------------------------------- |
| MCP          | `mcp`      | `mcp.json` à la racine du paquet (même schéma que le MCP utilisateur/workspace)                    |
| Agent hooks  | `hooks`    | `hooks.json` à la racine du paquet (même schéma que les hooks agent ; pas `contributes.cli.hooks`) |
| Skills       | `skills`   | `skills/<name>/SKILL.md`                                                                           |
| Rules        | `rules`    | `rule.md` à la racine du paquet                                                                    |

Déclaré mais fichier manquant ou invalide : l'installation échoue. Les fichiers non déclarés sont ignorés et jamais chargés.

Les `command` et `cwd` relatifs sont résolus par rapport à la racine de l'extension. Si un MCP stdio omet `cwd`, la racine de l'extension est utilisée.

Ces contributions sont superposées dans la session lorsque l'extension est activée. Elles n'apparaissent pas dans **Paramètres → MCPs | Hooks | Skills | Rules**. En cas de conflit de nom : workspace > utilisateur > extension.

### `settingsSchema`

| Champ          | Description                                                       |
| -------------- | ----------------------------------------------------------------- |
| `key`          | Requis. Même modèle que les noms d'outils                         |
| `type`         | Requis. `string`, `boolean`, `number` ou `select`                 |
| `title`        | Requis. Libellé de l'interface                                    |
| `description`  | Optionnel                                                         |
| `placeholder`  | Optionnel                                                         |
| `required`     | Optionnel. Booléen                                                |
| `defaultValue` | Optionnel. Doit correspondre à `type`                             |
| `options`      | Requis pour `select`. Tableau de `{ value, label, description? }` |

Les valeurs sont `string`, `number`, `boolean` ou `null`. `null` efface un réglage non requis.

### `secretSlots`

| Champ         | Description        |
| ------------- | ------------------ |
| `key`         | Requis             |
| `title`       | Requis             |
| `description` | Optionnel          |
| `required`    | Optionnel. Booléen |

Desktop stocke les secrets dans le trousseau du système d'exploitation. Sur le chemin du démon CLI, `secrets.set` / `secrets.delete` peuvent ne pas être disponibles.

## `activate`

`main` est chargé avec `import` dynamique. Exportez l'un des éléments suivants :

- `export function activate(ctx) { ... }`
- `export default function activate(ctx) { ... }`
- `export default { activate }`

### `ctx`

| Champ             | Description                                                                                                   |
| ----------------- | ------------------------------------------------------------------------------------------------------------- |
| `extension`       | `{ id, name, version, directoryPath, manifestPath, main }`                                                    |
| `host`            | API hôte. Desktop implémente `showMessageBox`. CLI est `{}`                                                   |
| `log`             | `(message: string) => void`                                                                                   |
| `settings`        | `get(key)`, `getAll()`, `set(key, value)`, `setAll(values)`                                                   |
| `secrets`         | `get(key)`, `has(key)`, `set(key, value)`, `delete(key)` — les clés doivent être déclarées dans `secretSlots` |
| `activationEvent` | Facultatif. `{ type, detail? }`                                                                               |

### Valeur de retour

Renvoie un objet, ou exportez les mêmes champs depuis le module.

| Champ             | Description                                                                             |
| ----------------- | --------------------------------------------------------------------------------------- |
| `tools`           | `Record<string, (ctx) => unknown>`. Les clés sont les noms d'outils du manifeste        |
| `invokeTool`      | `(ctx) => unknown`. Utilisé à la place de `tools[name]` lorsque présent                 |
| `systemPrompt`    | Fragment système statique                                                               |
| `getSystemPrompt` | `() => string \| Promise<string>`. Utilisé à la place de `systemPrompt` lorsque présent |
| `onEvent`         | `(event) => void`                                                                       |
| `dispose`         | `() => void`. Appelé lors de la suppression ou du rechargement                          |

### Contexte `ctx` du gestionnaire d'outil

| Champ             | Description                                                    |
| ----------------- | -------------------------------------------------------------- |
| `extension`       | Mêmes informations d'exécution que `activate`                  |
| `host`            | Même API hôte                                                  |
| `toolName`        | Nom d'outil du manifeste                                       |
| `arguments`       | Objet provenant du modèle                                      |
| `log`             | Même journaliseur                                              |
| `settings`        | Même accesseur de paramètres                                   |
| `secrets`         | Même accesseur de secrets                                      |
| `toolCallId`      | Facultatif                                                     |
| `questionsResult` | Facultatif. Défini lorsque `approvalMode` est `need-questions` |

Un résultat `string` est transmis tel quel. Les autres valeurs sont `JSON.stringify(value, null, 2)`. `undefined` devient `""`.

### Desktop `host.showMessageBox`

| Champ       | Description                                                |
| ----------- | ---------------------------------------------------------- |
| `title`     | Requis. Chaîne de caractères                               |
| `message`   | Requis. Chaîne de caractères                               |
| `detail`    | Facultatif. Chaîne de caractères                           |
| `buttons`   | Facultatif. Tableau de chaînes                             |
| `cancelId`  | Facultatif. Nombre                                         |
| `defaultId` | Facultatif. Nombre                                         |
| `noLink`    | Facultatif. Booléen                                        |
| `type`      | Facultatif. `none`, `info`, `error`, `question`, `warning` |

```js
export function activate(ctx) {
  return {
    systemPrompt: "Use lookup_item when the user asks for an item by id.",
    async invokeTool({ toolName, arguments: args, settings, secrets }) {
      if (toolName !== "lookup_item") {
        throw new Error(`Unknown tool: ${toolName}`);
      }
      const region = await settings.get("region");
      const token = await secrets.get("api_token");
      return { id: args.id, region, hasToken: Boolean(token) };
    },
    dispose() {
      ctx.log("example-extension disposed");
    },
  };
}
```

## Distribuer en ZIP

Empaquetez un répertoire d'extension dans le format ZIP partageable (contenu plus `.spirit/extension.json`) :

```bash
npx @spiritagent/extension-toolkit pack ./my-extension
```

La commande valide d'abord le paquet puis écrit `<name>-<version>.zip` dans le répertoire courant. Les utilisateurs importent le ZIP depuis la page **Extensions** ou avec `spirit extension import` ; il aboutit dans leur marché Personnel. Voir [Extensions](../customize/extensions.mdx).

## Héberger un marché d'extensions distant

Un marché d'extensions distant est un répertoire servable avec un index `.spirit/marketplace.json` : un dépôt Git, un site statique ou un répertoire local. Les utilisateurs l'ajoutent avec `spirit extension marketplace add <url|path>` ou depuis la page **Extensions** de Desktop, puis parcourent et installent ses entrées.

<Tabs items={["Dépôt modèle", "Manuel"]}>
<Tab value="Dépôt modèle">

[Use this template](https://github.com/new?template_owner=SpiritAgents&template_name=extension-template) crée votre propre dépôt de marché à partir de `SpiritAgents/extension-template`.

Le modèle fournit la structure de registre, deux extensions d'exemple et une CI qui valide le registre à chaque push et pull request. Pour publier une extension :

1. Générez-la avec `npm create @spiritagent/extension`.
2. Déplacez le dossier de l'extension dans `extensions/`.
3. Ajoutez l'entrée de registre affichée par l'assistant à `.spirit/marketplace.json`.
4. Poussez — les utilisateurs ajoutent le marché avec son URL Git.

</Tab>
<Tab value="Manuel">

Une racine de marché contient l'index plus un répertoire de contenu par extension :

```text
my-marketplace/
  .spirit/
    marketplace.json  # l'index
  extensions/
    my-extension/     # répertoire de contenu (paquet npm simple + fichiers de capacités)
      icon.svg
      package.json
      ...
```

Les chemins relatifs dans `marketplace.json` se résolvent par rapport à la racine du marché et ne doivent contenir ni segments `..` ni chemins absolus.

Champs d'entrée, par groupe :

- **Identité** — `name` (kebab-case ; l'id d'entrée), `version` (semver, sans pré-version) et `source` : une chaîne de chemin relatif à la racine comme `"./extensions/my-extension"` pour du contenu local, ou `{ "source": "npm", "package": "@scope/name@1.0.0" }` pour épingler une version npm exacte (l'intégrité est vérifiée contre le hachage SRI du packument à l'installation).
- **Affichage** — `displayName`, `description`, `icon` (chemin SVG relatif à la racine), `category`, `keywords`, `author`.
- **Déclaration** — `manifest` : la déclaration d'exécution décrite dans la section « Le `manifest` ». Le marché la cautionne ; un paquet ne peut pas affirmer des capacités de lui-même.
- **Curation** — `featured` et `reviewStatus` (`unverified` / `verified` / `revoked`).

Validez le registre localement — hors ligne : schéma, noms kebab-case, semver sans pré-version, format des sources npm, fichiers de contribution déclarés pour les sources locales et règles d'icône :

```bash
npx -y @spiritagent/extension-toolkit marketplace check .
```

Discipline de vérification : les pull requests qui ajoutent une entrée ou modifient sa `version` doivent conserver `reviewStatus: "unverified"` ; la promotion en `verified` se fait dans un commit séparé après une revue humaine. Le `.github/workflows/marketplace.yml` du dépôt modèle est une implémentation de référence — il diff l'index contre la base de la PR.

</Tab>
</Tabs>

### Marchés locaux

Tout répertoire local contenant un `.spirit/marketplace.json` fonctionne comme un marché — ajoutez-le avec `spirit extension marketplace add <path>` ou **Ajouter depuis le disque…** sur Desktop. Les marchés locaux sont lus sur place et n'ont pas besoin de CI, ce qui en fait la boucle de développement des auteurs d'extensions : modifier, réinstaller, recommencer.
