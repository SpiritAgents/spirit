每個高風險工具呼叫都可以等待您核准。{{product.name|mdx}} 有三個核准層級。Desktop 顯示為 **預設核准**、**自動核准** 和 **略過核准**。CLI 使用 `/approval` 或 `-a`。

| 層級     | ID                | 行為                                                                     |
| -------- | ----------------- | ------------------------------------------------------------------------ |
| 預設核准 | `default`         | 您自行核准檔案編輯、Shell 及其他高風險工具。                             |
| 自動核准 | `auto-approval`   | 次要語言模型會審查高風險呼叫。除非該審查（或掛鉤）要求，否則不會提示您。 |
| 略過核准 | `bypass-approval` | 高風險工具執行時不會顯示核准提示。`deny` 規則仍適用。                    |

## 權限允許清單

在核准層級之上，`config.json` 可以明確限定個別命令與路徑可執行的操作。規則位於頂層 `permission` 欄位下，按工具名稱分組：

```json
{
  "schemaVersion": 1,
  "permission": {
    "shell": {
      "git *": "allow",
      "git push *": "ask",
      "rm -rf *": "deny",
      "sudo *": "deny"
    },
    "read_file": {
      "*": "allow",
      "*/.env*": "ask",
      "~/.ssh/*": "deny"
    }
  }
}
```

每個鍵都是模式，每個值都是動作：

| 動作    | 效果                                                                        |
| ------- | --------------------------------------------------------------------------- |
| `allow` | 執行時不提示                                                                |
| `ask`   | 顯示核准提示                                                                |
| `deny`  | 直接拒絕。不提示；模型會收到 `[denied by permission rule] …` 的工具失敗結果 |

`read_file` 規則也涵蓋 `ls` 的外部路徑檢查。之後可能會加入更多領域。

### 模式語法

- `*` 比對零個或多個任意字元，包括 `/`。其餘字元皆為字面比對。不支援 `?`、`[]` 或 `{}`。
- 完整字串比對，區分大小寫。
- 以 `" *"` 結尾的模式也會比對裸命令：`"git *"` 同時比對 `git` 和 `git status`。

規則順序不影響結果：任何符合的 `deny` 優先，其次是 `ask`，再來是 `allow`。沒有任何符合時，shell 會後備為 `ask`（fail-safe）。請注意，`"*": "ask"` 條目會比對所有內容，因此會蓋過每條 `allow` 規則——fail-safe 在無符合時本來就會詢問，所以比對全部的 `ask` 條目只能作為文件說明，不能作為後備。

### deny 是絕對的

`deny` 規則無法被規則順序、工作階段記憶、傳回 `allow` 的掛鉤、`bypass-approval` 層級，或您自行啟動的工具執行所覆寫。

### 複合 Shell 命令

{{product.name|mdx}} 會將 shell 命令拆分為實際會執行的簡單命令——尊重引號與跳脫字元，涵蓋 `&&`、`||`、`;`、`|`、`|&`、`&`、換行與子 shell，包括 `$(...)` 與反引號內容——並逐一評估每個區段。只要有一個區段被拒絕，整個命令就會被拒絕。{{product.name|mdx}} 無法解析的命令會保守地改為詢問。

### read_file 路徑

模式比對的是正規化（realpath）後的絕對路徑。開頭的 `~/` 會展開為您的家目錄。以 `*` 開頭的模式視為絕對——開頭的萬用字元會吸收根分隔符，因此 `*` 和 `"*/.env*"` 可比對任何位置的正規化路徑。以字面相對區段開頭的模式（例如 `"src/*.ts"`）具有工作區相對語意：僅比對目前工作區內的路徑，絕不比對外部路徑，並會產生設定 lint 警告。

沒有規則符合時，會套用內建的位置後備：工作區內部與 {{product.name|mdx}} 管理的路徑為 allow，其他外部路徑為 ask。規則也可以收緊工作區內部路徑——`"*/.env*": "ask"` 在工作區內同樣有效。

無效條目（空模式、未知動作、非物件區塊）會被捨棄並產生 lint 警告。

## 記住核准

核准提示提供三個選項：

- **允許一次** — 僅執行本次呼叫。
- **永遠允許** — 將一條完全符合的 `allow` 規則（原始命令或正規化路徑）附加到 config.json 中的 `permission.shell` / `permission.read_file`。不會推斷萬用字元。
- **拒絕** — 拒絕，並可提供模型會閱讀的選填自由文字指引。

MCP 與內建 lazy-gateway 工具的核准皆為一次性；不提供記住選項。在預設與自動核准下，MCP `tool_call` 僅在工具宣告 `readOnlyHint: true` 且 `openWorldHint: false` 時才會跳過提示。缺少這些提示時遵循規格預設值（非唯讀、開放世界），仍會詢問；開放世界的唯讀工具與內建 lazy-gateway 呼叫亦然。透過 [ACP](../acp.mdx) 時，「永遠允許」僅限當前工作階段，且不提供儲存至 config.json 的功能；工作階段記憶永遠不會覆寫 `deny` 規則。

## 掛鉤只會收緊，絕不放寬

[preToolUse 掛鉤](../customize/hooks.mdx)會在允許清單評估之前執行，且只能收緊或封鎖。掛鉤的 `deny` 或允許清單的 `deny` 都會拒絕；掛鉤的 `ask` 或允許清單的 `ask` 都會提示；掛鉤傳回 `allow` 不會跳過主機核准。

## 略過核准不會跳過的項目

`bypass-approval` 仍會阻止以下情況：

- 允許清單中的 `deny` 規則
- [ask_questions](./ask-questions.mdx)
- 需要問題的擴充功能流程
- 在 `preToolUse` 上傳回 `ask` 的掛鉤

自動核准也無法覆寫掛鉤的 `ask`。

## 離線測試規則

```bash
spirit permission check --shell "git push origin main"
spirit permission check --read-file ~/.ssh/id_rsa
```

印出判定結果、符合的規則以及逐區段細節，而不實際執行任何操作。評估在守護程式端執行，因此需要可連線的 {{product.name|mdx}} 守護程式。

目前尚無規則的設定介面。請編輯 `config.json` 並使用 `spirit permission check` 驗證。

## 何時使用哪一種

在您看過智慧體做出幾次好的編輯之前，請保持**預設**。當您想要速度但仍想要二次檢查時，請使用**自動核准**。僅在一次性分支或您正在觀看的任務上使用**略過**。

無頭模式的 `spirit -p` 若呼叫需要核准則會失敗。請傳入 `-a auto-approval` 或 `-a bypass-approval`，或改用 TUI。`allow` 規則在那裡同樣會在不提示的情況下執行。
