每个高风险工具调用都可以先等你确认。{{product.name|mdx}} 有三档审批。Desktop 显示为 **默认审批**、**自动审批** 和 **绕过审批**。CLI 使用 `/approval` 或 `-a`。

| 档位     | Id                | 行为                                                                                     |
| -------- | ----------------- | ---------------------------------------------------------------------------------------- |
| 默认审批 | `default`         | 文件编辑、shell 和其他高风险工具由你逐一审批。                                           |
| 自动审批 | `auto-approval`   | 次要语言模型审查高风险调用。除非这次审查（或某个挂钩）要求询问，否则不再弹出审批提示。 |
| 绕过审批 | `bypass-approval` | 高风险工具不经审批提示直接运行。`deny` 规则仍然生效。                                    |

## 权限允许列表

在审批档位之上，`config.json` 可以精确规定单个命令和路径能做什么。规则位于顶层 `permission` 字段下，按工具名分组：

```json
{
  "schemaVersion": 1,
  "permission": {
    "shell": {
      "git *": "allow",
      "git push *": "ask",
      "rm -rf *": "deny",
      "sudo *": "deny"
    },
    "read_file": {
      "*": "allow",
      "*/.env*": "ask",
      "~/.ssh/*": "deny"
    }
  }
}
```

每个键是一个模式，每个值是一个动作：

| 动作    | 效果                                                                                |
| ------- | ----------------------------------------------------------------------------------- |
| `allow` | 不经提示直接运行                                                                    |
| `ask`   | 显示审批提示                                                                        |
| `deny`  | 直接拒绝。不弹出提示；模型会收到一条 `[denied by permission rule] …` 的工具失败结果 |

`read_file` 规则同时覆盖 `ls` 的外部路径检查。之后可能支持更多工具域。

### 模式语法

- `*` 匹配零个或多个任意字符，包括 `/`。其余字符均为字面量。不支持 `?`、`[]` 或 `{}`。
- 整串匹配，区分大小写。
- 以 `" *"` 结尾的模式也匹配裸命令：`"git *"` 同时匹配 `git` 和 `git status`。

规则顺序无关紧要：任何匹配的 `deny` 优先，其次是 `ask`，最后是 `allow`。没有任何规则匹配时，shell 回落到 `ask`（失败安全）。注意 `"*": "ask"` 条目会匹配一切，因此压过所有 `allow` 规则——失败安全在无匹配时已经会询问，所以全匹配 `ask` 条目只能当作文档，不能当作兜底。

### `deny` 是绝对的

`deny` 规则无法被规则顺序、会话记忆、返回 `allow` 的挂钩、`bypass-approval` 档位或你自己发起的工具运行所覆盖。

### 复合 shell 命令

{{product.name|mdx}} 会把一条 shell 命令拆成实际会执行的简单命令——尊重引号和转义，跨 `&&`、`||`、`;`、`|`、`|&`、`&`、换行和子 shell，包括 `$(...)` 和反引号的内容——并逐段评估。只要有一段被拒绝，整条命令即被拒绝。{{product.name|mdx}} 无法解析的命令会保守地要求审批。

### read_file 路径

模式匹配的是规范化（realpath）后的绝对路径。开头的 `~/` 会展开为你的主目录。以 `*` 开头的模式按绝对路径处理——开头的通配符会吸收根分隔符，因此 `*` 和 `"*/.env*"` 可以匹配任何位置的规范路径。以字面相对段开头的模式（例如 `"src/*.ts"`）具有工作区相对语义：只匹配当前工作区内的路径，绝不匹配工作区外的路径，并会产生一条配置 lint 警告。

当没有规则匹配时，应用内置的位置兜底：工作区内部和由 {{product.name|mdx}} 管理的路径为允许，其他外部路径为询问。规则也可以收紧工作区内部路径——`"*/.env*": "ask"` 在工作区内同样生效。

无效条目（空模式、未知动作、非对象块）会被丢弃，并产生 lint 警告。

## 记住审批决定

审批提示提供三个选项：

- **允许一次**——只运行这一次调用。
- **始终允许**——向 config.json 的 `permission.shell` / `permission.read_file` 追加一条精确匹配的 `allow` 规则（原样的命令或规范路径）。不做通配符推断。
- **拒绝**——拒绝这次调用，可附带一段供模型阅读的自由文本说明。

MCP 与内置 lazy-gateway 工具的审批都是一次性的，不提供记住选项。在默认审批和自动审批下，MCP `tool_call` 仅当工具声明了 `readOnlyHint: true` 且 `openWorldHint: false` 时才跳过提示。缺失的 hint 按规范默认值处理（非只读、开放世界），仍然会询问；开放世界的只读工具和内置 lazy-gateway 调用也一样会询问。通过 [ACP](../acp.mdx) 时，「始终允许」只在会话范围内生效，不暴露持久化到 config.json 的选项；会话记忆永远不能覆盖 `deny` 规则。

## 挂钩只会收紧，不会放宽

[preToolUse 挂钩](../customize/hooks.mdx) 在允许列表评估之前运行，只能收紧或阻止。挂钩的 `deny` 或允许列表的 `deny` 都会拒绝；挂钩的 `ask` 或允许列表的 `ask` 都会弹出提示；挂钩返回 `allow` 不会跳过宿主审批。

## 绕过审批不会跳过的环节

`bypass-approval`（以及你自己发起的工具运行）只是把 `ask` 折叠成 `allow`。以下情况仍然会停下：

- 允许列表中的 `deny` 规则
- [ask_questions](./ask-questions.mdx)
- 需要提问的扩展流程
- 在 `preToolUse` 返回 `ask` 的挂钩

自动审批同样无法覆盖挂钩的 `ask`。

## 离线测试规则

```bash
spirit permission check --shell "git push origin main"
spirit permission check --read-file ~/.ssh/id_rsa
```

打印判定结果、命中的规则和逐段细节，不实际运行任何东西。评估在守护进程侧进行，因此需要一个可连接的 {{product.name|mdx}} 守护进程。

规则目前还没有设置界面。编辑 `config.json`，并用 `spirit permission check` 验证。

## 什么时候用哪一档

先留在 **default**，等你看到 Agent 做出几次可靠的编辑后再调整。想要速度但仍想保留一道复查时，使用 **auto-approval**。**bypass** 只在一次性分支或你确认可控的任务上使用。

非交互的 `spirit -p` 在遇到需要审批的调用时会失败。传入 `-a auto-approval` 或 `-a bypass-approval`，或改用 TUI。`allow` 规则在那里同样不经提示直接运行。
