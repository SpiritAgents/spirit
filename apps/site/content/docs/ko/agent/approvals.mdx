모든 위험한 도구 호출은 사용자의 승인을 기다릴 수 있습니다. {{product.name|mdx}}에는 세 가지 승인 수준이 있습니다. Desktop에서는 **Default Approval**, **Auto Approval**, **Bypass Approval**로 표시됩니다. CLI에서는 `/approval` 또는 `-a`를 사용합니다.

| 수준      | ID                | 동작                                                                                                             |
| --------- | ----------------- | ---------------------------------------------------------------------------------------------------------------- |
| 기본 승인 | `default`         | 파일 편집, 셸 및 기타 고위험 도구를 직접 승인합니다.                                                             |
| 자동 승인 | `auto-approval`   | 보조 언어 모델이 고위험 호출을 검토합니다. 해당 검토(또는 후크)가 요청하지 않는 한 프롬프트가 표시되지 않습니다. |
| 우회 승인 | `bypass-approval` | 고위험 도구가 승인 프롬프트 없이 실행됩니다. `deny` 규칙은 여전히 적용됩니다.                                    |

## 권한 허용 목록

승인 수준 위에, `config.json`은 개별 명령과 경로가 무엇을 할 수 있는지 고정할 수 있습니다. 규칙은 최상위 `permission` 필드 아래에 있으며 도구 이름별로 그룹화됩니다:

```json
{
  "schemaVersion": 2,
  "permission": {
    "shell": {
      "git *": "allow",
      "git push *": "ask",
      "rm -rf *": "deny",
      "sudo *": "deny"
    },
    "read_file": {
      "*": "allow",
      "*/.env*": "ask",
      "~/.ssh/*": "deny"
    }
  }
}
```

각 키는 패턴이고 각 값은 액션입니다:

| 액션    | 효과                                                                                                    |
| ------- | ------------------------------------------------------------------------------------------------------- |
| `allow` | 프롬프트 없이 실행합니다                                                                                |
| `ask`   | 승인 프롬프트를 표시합니다                                                                              |
| `deny`  | 즉시 거부합니다. 프롬프트 없음; 모델은 `[denied by permission rule] …` 도구 실패 결과를 받습니다 |

`read_file` 규칙은 `ls`의 외부 경로 검사에도 적용됩니다. 더 많은 도메인이 나중에 추가될 수 있습니다.

### 패턴 구문

- `*`는 `/`를 포함한 모든 문자의 0개 이상과 일치합니다. 그 외의 문자는 모두 리터럴입니다. `?`, `[]`, `{}`는 없습니다.
- 전체 문자열 일치, 대소문자 구분.
- `" *"`로 끝나는 패턴은 단독 명령과도 일치합니다: `"git *"`는 `git`과 `git status` 모두와 일치합니다.

규칙 순서는 중요하지 않습니다: 일치하는 `deny`가 이기고, 그다음 `ask`, 그다음 `allow`입니다. 아무것도 일치하지 않으면 셸은 `ask`로 폴백합니다(fail-safe). `"*": "ask"` 항목은 모든 것과 일치하므로 모든 `allow` 규칙보다 우선한다는 점에 주의하세요——fail-safe가 이미 일치하는 것이 없을 때 묻기 때문에, 전체 일치 `ask` 항목은 폴백이 아니라 문서화 용도로만 유용합니다.

### `deny`는 절대적입니다

`deny` 규칙은 규칙 순서, 세션 메모리, `allow`를 반환하는 후크, `bypass-approval` 수준 또는 직접 시작하는 도구 실행으로 재정의할 수 없습니다.

### 복합 셸 명령

{{product.name|mdx}}은 셸 명령을 실행될 단순 명령들로 분할하고——따옴표와 이스케이프를 존중하며, `&&`, `||`, `;`, `|`, `|&`, `&`, 개행, 서브셸(`$(...)` 및 백틱 내용 포함) 전반에 걸쳐——각 세그먼트를 평가합니다. 하나의 세그먼트가 거부되면 전체 명령이 거부됩니다. {{product.name|mdx}}이 파싱할 수 없는 명령은 보수적으로 묻습니다.

### `read_file` 경로

패턴은 캐노니컬(realpath) 절대 경로와 일치합니다. 시작의 `~/`는 홈 디렉터리로 확장됩니다. `*`로 시작하는 패턴은 절대 경로로 간주됩니다——선행 와일드카드가 루트 구분자를 흡수하므로 `*`와 `"*/.env*"`는 어디서든 캐노니컬 경로와 일치합니다. 리터럴 상대 세그먼트로 시작하는 패턴(예: `"src/*.ts"`)은 작업공간 상대 의미를 가집니다: 현재 작업공간 내부 경로와만 일치하고 외부 경로와는 절대 일치하지 않으며, config lint 경고를 생성합니다.

일치하는 규칙이 없으면 내장 위치 폴백이 적용됩니다: 작업공간 내부 및 {{product.name|mdx}} 관리 경로는 allow, 그 외 외부 경로는 ask입니다. 규칙은 작업공간 내부 경로도 강화할 수 있습니다——`"*/.env*": "ask"`는 작업공간 내부에서도 작동합니다.

유효하지 않은 항목(빈 패턴, 알 수 없는 액션, 객체가 아닌 블록)은 lint 경고와 함께 삭제됩니다.

## 승인 기억하기

승인 프롬프트는 세 가지 선택지를 제공합니다:

- **Allow once** — 이 호출만 실행합니다.
- **Always Allow** — 정확히 일치하는 `allow` 규칙(그대로의 명령 또는 캐노니컬 경로)을 config.json의 `permission.shell` / `permission.read_file`에 추가합니다. 와일드카드 추론은 없습니다.
- **Deny** — 거부하며, 모델이 읽는 자유 형식 텍스트 안내를 선택적으로 포함할 수 있습니다.

MCP 및 내장 lazy-gateway 도구 승인은 일회성이며 기억 기능이 제공되지 않습니다. 기본 및 자동 승인에서 MCP `tool_call`은 도구가 `readOnlyHint: true`와 `openWorldHint: false`를 선언할 때만 프롬프트를 건너뜁니다. 누락된 힌트는 스펙 기본값(읽기 전용 아님, 오픈 월드)을 따르므로 여전히 묻고, 오픈 월드 읽기 전용 도구와 내장 lazy-gateway 호출도 마찬가지입니다. [ACP](../acp.mdx)에서 "allow always"는 세션 범위이며 config.json에 지속하는 기능은 노출되지 않습니다. 세션 메모리는 `deny` 규칙을 절대 재정의하지 않습니다.

## 후크는 강화만 하고 완화하지 않습니다

[preToolUse 후크](../customize/hooks.mdx)는 허용 목록 평가 전에 실행되며 강화하거나 차단만 할 수 있습니다. 후크 `deny` 또는 허용 목록 `deny`는 거부하고, 후크 `ask` 또는 허용 목록 `ask`는 묻습니다. `allow`를 반환하는 후크는 호스트 승인을 건너뛰지 않습니다.

## 우회가 건너뛰지 않는 항목

`bypass-approval`도 다음 경우에는 중지됩니다:

- 허용 목록의 `deny` 규칙
- [ask_questions](./ask-questions.mdx)
- 질문이 필요한 확장 프로그램 흐름
- `preToolUse`에서 `ask`를 반환하는 후크

자동 승인 역시 후크의 `ask`를 재정의할 수 없습니다.

## 오프라인으로 규칙 테스트하기

```bash
spirit permission check --shell "git push origin main"
spirit permission check --read-file ~/.ssh/id_rsa
```

아무것도 실행하지 않고 판정, 일치한 규칙, 세그먼트별 세부 정보를 출력합니다. 평가는 데몬 측에서 실행되므로 접근 가능한 {{product.name|mdx}} 데몬이 필요합니다.

아직 규칙용 설정 UI는 없습니다. `config.json`을 편집하고 `spirit permission check`로 검증하세요.

## 사용 중단: tool-permissions.json

<Callout type="warn" title="사용 중단">

이전 "Always Trust" 버튼이 작성하던 정확히 일치하는 저장소인 `tool-permissions.json`은 더 이상 읽거나 쓰지 않습니다. 남은 파일은 비활성이므로 수동으로 삭제하세요. 자동 마이그레이션은 없습니다——여전히 필요한 규칙을 `config.json`의 `permission` 아래에 다시 만드세요.

</Callout>

## 언제 무엇을 사용해야 하는가

에이전트가 몇 번의 올바른 편집을 수행하는 것을 확인할 때까지 **기본**으로 유지하세요. 속도를 원하지만 두 번째 확인을 원할 때 **자동 승인**을 사용하세요. **우회**는 임시 브랜치 또는 지켜보고 있는 작업에서만 사용하세요.

헤드리스 `spirit -p`는 호출에 승인이 필요한 경우 실패합니다. `-a auto-approval` 또는 `-a bypass-approval`을 전달하거나 TUI를 사용하세요. `allow` 규칙도 거기에서 프롬프트 없이 실행됩니다.
